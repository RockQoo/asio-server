TestClient가 패킷을 보내면 Gateway/World/Zone은 어떻게 동작하나

예전에는 TestClient가 ZoneServer에 직접 접속했지만, 지금은 GatewayServer → WorldServer → ZoneServer 3계층을 거친다(존 핸드오프/Mail 다이어그램과 짝을 이루는 기본 패킷 왕복 경로). 실제 소스(GatewayServer/Src/Handler/ClientLinkHandler.cpp, WorldServer/Src/Handler/GatewayLinkHandler.cpp, ZoneServer/Src/Handler/WorldLinkHandler.cpp, ZoneServer/Src/Game/ZoneWorld.cpp)를 그대로 따라간 흐름이다.

● TestClient (별도 프로세스) ● I/O 스레드 (릴레이/라우팅만, 게임 상태 없음) ● 로직 스레드 (TaskWorker, CPU affinity 고정)
접속 직후(이 다이어그램 이전 시점): Gateway가 클라이언트를 accept하면 ClientConnected를 World로 보내고, World는 기본 존(zoneId=0)에 EnterZoneRequest를 보낸다. Zone이 OnPlayerEnter로 플레이어를 만들고 EnterZoneNotify를 되돌려 보내는 것까지가 그 과정이다 -- 아래 흐름은 그 다음, 클라이언트가 실제 게임 패킷을 보낸 이후를 다룬다.

1. 클라이언트가 패킷을 만들어 보낸다 (여기까지는 예전과 동일)

TestClient
echo / move / chat 명령 입력
Packet::BuildFrame(packetId, payload)로 [bodySize:2][id:2][payload...] 프레임을 만들어 Gateway의 클라이언트 포트(9000)로 그대로 전송한다. 클라이언트 프로토콜 자체는 3계층으로 나뉘기 전과 한 글자도 다르지 않다 -- Gateway/World는 이 바이트를 그대로 옮길 뿐이다.
↓ TCP
I/O 스레드 (GatewayServer)
ClientLinkHandler::OnPacket
받은 패킷 앞에 ClientEnvelopeHeader{clientSessionId, innerPacketId}를 얹어 FromClient로 World에 그대로 전달한다. 내용물(Echo인지 Move인지)은 전혀 해석하지 않는다 -- 순수 릴레이.
↓ TCP (Gateway↔World 전용 연결)
I/O 스레드 (WorldServer)
GatewayLinkHandler::HandleFromClient
ClientEnvelopeHeader.clientSessionId만 들여다보고 ClientRegistry에서 이 클라이언트의 현재 zoneId를 조회한 뒤, 바디를 그대로 그 존의 연결로 ForwardToZone 전송한다.
↓ TCP (World↔Zone 전용 연결)
I/O 스레드 (ZoneServer)
WorldLinkHandler::HandleForwardToZone
ClientEnvelopeHeader.innerPacketId로 실제 패킷 타입을 가려낸다. 여기까지는 아직 게임 상태를 전혀 건드리지 않는다.

2. 패킷 타입에 따라 갈라진다

Echo — 공유 상태 불필요
I/O 스레드 (ZoneServer)
DispatchInnerPacket의 Echo 분기
존 워커로 넘기지 않고 그 자리에서 바로 같은 envelope을 ForwardToWorld로 되돌려 보낸다 -- 예전 HandleEcho와 동기가 같다: 존 상태가 필요 없는 유일한 예외 경로.
Move / Chat — 존 상태 변경 필요
I/O 스레드 (ZoneServer)
DispatchInnerPacket의 Move/Chat 분기
innerPayload를 소유한 값으로 복사한다(MovePacket 구조체 복사 / std::string message 이동). payload는 이 함수가 끝나면 I/O 스레드가 재사용할 버퍼를 가리키므로 그대로 넘기면 안 된다.
↓ PostTask (스레드 경계)
로직 스레드 (TaskWorker)
ZoneWorld::OnMove / OnChat
이 존 전용 CPU 코어에 고정된 스레드에서 실행. players_[clientSessionId]를 락 없이 갱신한다 -- 존 서버 프로세스 자체가 이 존 하나만 담당하므로, 이 프로세스가 곧 이 존의 유일한 로직 스레드다. (OnMove는 x가 구간을 벗어나면 대신 핸드오프를 요청한다 -- 별도 다이어그램 참고.)
↓
로직 스레드 (TaskWorker)
ZoneWorld::BroadcastToZone
같은 존의 players_를 순회하며(본인 포함) 플레이어마다 SendToPlayer로 별도 envelope을 만들어 World와의 연결 하나 위에 다중화해 보낸다 -- 이제 Zone은 클라이언트 소켓을 직접 갖지 않기 때문이다.

3. 다시 클라이언트로 (왕복 경로를 그대로 거슬러 올라간다)

I/O 스레드 (WorldServer)
ZoneLinkHandler::HandleForwardToWorld
clientSessionId로 ClientRegistry에서 Gateway 세션을 찾아 같은 바디를 ToClient로 그대로 전달한다.
↓
I/O 스레드 (GatewayServer)
WorldLinkHandler::HandleToClient
envelope을 벗기고 innerPacketId/원본 바디만 남겨 로컬 클라이언트 세션에 SendPacket한다.
↓ TCP
TestClient
ReceiveLoop 스레드가 응답 출력
[recv] Echo: ... / [recv] Move x=.. y=.. / [recv] Chat from N: ...로 콘솔에 찍힌다 -- 3계층을 거쳤다는 것을 클라이언트는 전혀 알 수 없다.
핵심 불변식: Gateway/World의 I/O 스레드는 clientSessionId 태그만 보고 라우팅할 뿐 패킷 내용을 해석하지 않는다. 게임 상태(ZoneWorld)는 여전히 그 존을 담당하는 프로세스의 로직 스레드에서만 직접 건드린다 -- 3계층으로 늘어났어도 "존 상태는 한 스레드에서만"이라는 원칙은 그대로다. 자세한 내용은 CLAUDE.md 참고.
