TestClient가 패킷을 보내면 Gateway/World/Zone은 어떻게 동작하나

예전에는 TestClient가 ZoneServer에 직접 접속했지만, 지금은 GatewayServer → WorldServer → ZoneServer 3계층을 거친다(존 핸드오프/Mail 다이어그램과 짝을 이루는 기본 패킷 왕복 경로). 특히 World와 Zone은 I/O 스레드에서 로직을 처리하지 않는다 -- World는 WorldWorker 단일 스레드로, Zone은 NETWORK → LB → BASIC → BROADCAST 순서로 스레드를 갈아타며 처리한다. 실제 소스(GatewayServer/Src/Handler/ClientLinkHandler.cpp, WorldServer/Src/Handler/GatewayLinkHandler.cpp, ZoneServer/Src/Handler/WorldLinkHandler.cpp, ZoneServer/Src/Game/ZoneWorld.cpp, ZoneServer/Src/Worker/BroadcastDispatcher.cpp)를 그대로 따라간 흐름이다.

● TestClient (별도 프로세스) ● NETWORK / I/O 스레드 (asio strand — 바이트 복사·릴레이만) ● 워커 스레드 (WorldWorker / LB / BASIC / BROADCAST)
ZoneServer의 5-풀 구조(이 페이지의 주인공): NETWORK(IoContextPool의 asio I/O 스레드) → LB(WorldLinkHandler가 소유, 패킷 파싱 + zoneId 판단) → BASIC(zoneId % basicThreadCount sticky, 게임 상태 전담) → BROADCAST(zoneId sticky, 팬아웃 전송) 4개가 이 경로에 등장하고, 나머지 하나인 TICK 풀은 패킷과 무관하게 RepeatingTimer가 ZoneWorld::Tick을 돌리는 용도라 여기엔 나타나지 않는다. 기본 스레드 수는 ZoneServer/Src/main.cpp에서 LB/BASIC/TICK/BROADCAST 전부 2개다.
접속 직후(이 다이어그램 이전 시점): Gateway가 클라이언트를 accept하면 ClientConnected를 World로 보내고, World(WorldWorker 스레드)는 기본 존(kDefaultEntryZoneId = 0)에 EnterZoneRequest를 보낸다. Zone의 LB 스레드가 그것을 받아 BASIC으로 넘기고, BASIC에서 ZoneWorld::OnPlayerEnter가 플레이어를 만들고 EnterZoneNotify를 되돌려 보내는 것까지가 그 과정이다 -- 아래 흐름은 그 다음, 클라이언트가 실제 게임 패킷을 보낸 이후를 다룬다.

1. 클라이언트 → Gateway → World → Zone (도착까지)

I/O 스레드 (GatewayServer)
ClientLinkHandler::OnPacket
받은 패킷 앞에 ClientEnvelopeHeader{clientSessionId, innerPacketId}를 얹어 FromClient로 World에 그대로 전달한다. 내용물(Echo인지 Move인지)은 전혀 해석하지 않는다 -- 순수 릴레이라 Gateway에는 워커 스레드 자체가 없고 I/O 스레드에서 바로 되돌려 보낸다.
↓ TCP (Gateway↔World 전용 연결)
I/O 스레드 (WorldServer, Session의 strand)
GatewayLinkHandler::OnPacket — 복사 후 PostTask만
여기서는 라우팅 판단을 전혀 하지 않는다. payload는 이 함수가 끝나면 I/O 스레드가 재사용할 버퍼라서 std::vector<byte>로 복사한 뒤 worldWorker_.PostTask(...)로 넘기는 게 전부다.
↓ PostTask (스레드 경계)
WorldWorker (World의 단일 처리 스레드)
GatewayLinkHandler::HandleFromClient
ClientEnvelopeHeader.clientSessionId만 들여다보고 ClientRegistry에서 이 클라이언트의 현재 zoneId를, ZoneLinkRegistry에서 그 존의 연결을 조회한 뒤 payload를 통째로 ForwardToZone으로 보낸다. 두 레지스트리는 이 스레드 하나만 건드리므로 락이 없다.
↓ TCP (World↔Zone 전용 연결)
NETWORK 스레드 (ZoneServer, Session의 strand)
WorldLinkHandler::OnPacket — 바이트만 복사
패킷 타입조차 해석하지 않는다. header.id와 payload 복사본을 캡처해 lbPool_.GetWorker(lbRoundRobin_++)로 라운드로빈 LB 워커에 PostTask한다(LB는 zoneId sticky가 아니다 -- 아직 zoneId를 모르니까).
↓ PostTask (스레드 경계)
LB 스레드 (ZoneServer, TaskWorker 풀)
WorldLinkHandler::DecodeAndDispatch → HandleForwardToZone
여기가 "recv 처리"의 실체다. ZoneLinkPacketId를 파싱해 EnterZoneRequest/LeaveZoneNotify/ForwardToZone을 가르고, ForwardToZone이면 clientLocalZone_(LB 스레드가 여럿이라 shared_mutex로 보호)에서 이 프로세스 안의 어느 zoneId인지를 찾는다. 게임 상태(ZoneWorld)는 아직 전혀 건드리지 않는다.

2. LB 스레드에서 갈라진다

Echo — 공유 상태 불필요
LB 스레드 (ZoneServer)
HandleForwardToZone의 innerPacketId == PacketId::Echo 분기
BASIC까지 가지 않고 이 LB 스레드에서 그대로 같은 envelope을 ForwardToWorld로 되돌려 보낸다 -- ZoneWorld::HandleClientPacket으로 넘기지 않는 유일한 예외 경로다 (존 상태가 필요 없으니 BASIC을 점유할 이유가 없다).
그 외(Move / Chat / MailAdd / MailDel) — 존 상태 필요
LB 스레드 (ZoneServer)
zoneWorkers_.PostToBasic(zoneId, ...)
innerPayload를 소유한 값으로 복사한 뒤 basicPool_.GetWorker(zoneId) -- 즉 zoneId % basicThreadCount로 항상 같은 BASIC 스레드에 맡긴다. LB는 패킷 내용이 뭔지 끝까지 들여다보지 않는다.
↓ PostTask (스레드 경계)
BASIC 스레드 (zoneId sticky)
ZoneWorld::HandleClientPacket
① players_에서 clientSessionId로 Player를 먼저 찾고 (입장하지 않았거나 이미 퇴장한 세션이면 여기서 버린다), ② Packet::PacketDispatcher<PacketId, PlayerState*>에 등록해둔 핸들러로 콜백한다. 와이어 포맷 파싱은 전부 여기서 일어난다.
↓ 등록된 핸들러 콜백
BASIC 스레드 (zoneId sticky)
ZoneWorld::HandleMove / HandleChat
players_를 락 없이 갱신한다 -- 한 프로세스가 존을 여러 개 호스팅해도(ZoneServer.exe 0,1) zoneId % basicThreadCount sticky 라우팅 때문에 같은 존의 패킷은 언제나 같은 BASIC 스레드 하나로만 오기 때문이다. (HandleMove는 x가 [xMin_, xMax_)를 벗어나면 갱신 대신 핸드오프를 요청한다 -- 별도 다이어그램 참고.)
↓
BASIC 스레드 (zoneId sticky)
ZoneWorld::BroadcastToZone — 스냅샷만 복사
여기서 직접 보내지 않는다. players_를 순회해 대상 clientSessionId 목록(std::vector)과 payload를 복사한 뒤 BroadcastDispatcher::Broadcast(zoneId, targets, ...)로 넘기고 끝낸다 -- BROADCAST 스레드가 players_ 맵을 직접 읽으면 BASIC과 동시 접근이 되어버리므로, 넘기는 건 반드시 스냅샷이어야 한다.
↓ PostTask (BASIC → BROADCAST, 또 한 번의 스레드 경계)
BROADCAST 스레드 (broadcastPool_.GetWorker(zoneId))
스냅샷을 돌며 팬아웃 전송
복사해 받은 targets마다 ClientEnvelopeHeader를 새로 만들어 ForwardToWorld로 World와의 연결 하나 위에 다중화해 보낸다(Zone은 클라이언트 소켓을 직접 갖지 않는다). 팬아웃 비용이 BASIC에서 빠져나가므로 인구가 많은 존에서도 BASIC이 다음 패킷을 계속 처리할 수 있다.

3. 다시 클라이언트로 (왕복 경로를 그대로 거슬러 올라간다)

I/O 스레드 (WorldServer, Session의 strand)
ZoneLinkHandler::OnPacket — 복사 후 PostTask만
Gateway 쪽과 대칭이다. 바이트를 복사해 WorldWorker로 넘기기만 하고 ClientRegistry는 건드리지 않는다.
↓ PostTask (스레드 경계)
WorldWorker (World의 단일 처리 스레드)
ZoneLinkHandler::HandleForwardToWorld
clientSessionId로 ClientRegistry에서 Gateway 세션을 찾아 같은 payload를 ToClient로 그대로 전달한다.
↓ TCP
I/O 스레드 (GatewayServer)
WorldLinkHandler::HandleToClient
envelope을 벗기고 innerPacketId/원본 바디만 남겨 로컬 클라이언트 세션에 SendPacket한다. Gateway는 워커가 없으므로 이것도 I/O 스레드에서 그대로 처리된다.
↓ TCP
TestClient
ReceiveLoop 스레드가 응답 출력
[recv] Echo: ... / [recv] Move x=.. y=.. / [recv] Chat from N: ...로 콘솔에 찍힌다 -- 3계층과 5개 풀을 거쳤다는 것을 클라이언트는 전혀 알 수 없다.
핵심 불변식: ① Gateway는 순수 릴레이라 I/O 스레드에서 끝나지만, World와 Zone의 I/O 스레드는 바이트를 복사해 넘기는 일만 한다 (World → WorldWorker, Zone → LB 풀). ② 게임 상태(ZoneWorld)를 건드리는 건 오직 BASIC 스레드뿐이고, zoneId % basicThreadCount sticky 라우팅이 "같은 존 = 같은 스레드"를 보장하기 때문에 players_에 락이 없다 -- 프로세스 개수나 한 프로세스가 맡은 존 개수와는 무관한 성질이다. ③ BASIC이 소유한 컨테이너는 다른 풀(TICK/BROADCAST)에 절대 그대로 넘기지 않고 스냅샷을 복사해 넘긴다. 자세한 내용은 CLAUDE.md 참고.
