우편 지급 + 골드 차감을 한 트랜잭션으로 — 뒤에서 실패하면 앞이 되돌아간다

C2ZMailBuy는 이 프로젝트에서 모델 두 개(우편함·지갑)를 한 요청에서 바꾸는 유일한 경로이고, 그래서 역순 롤백이 실제로 실행되는 유일한 경로다. 단일 모델 요청(C2ZMailAdd 등)은 실패 시점에 아직 바꾼 것이 없어서 롤백 코드가 한 번도 밟히지 않는다. 이 페이지는 (1) 성공 경로, (2) 잔액 부족으로 뒤에서 실패했을 때 앞의 변경이 되돌아가는 경로, (3) 롤백이 자기 자신을 다시 기록하지 않게 만드는 장치를 다룬다. 기본 패킷 왕복과 5-풀 구조는 Echo/Move/Chat 다이어그램, UnitOfWork 전송 경로는 Mail/UnitOfWork 다이어그램 참고.

● ProtocolClient (서버 워커 밖의 입력 주체) ● NETWORK / I/O 스레드 (바이트 복사·릴레이만) ● BASIC 워커 스레드 (그 존 전용, 락 없이 게임 상태 접근)

1. 성공 경로 — 태스크 2건이 한 응답으로 돌아온다

ProtocolClient
mail buy 선물 축하합니다 3600 100
제목/본문/유효기간(초)/가격을 보낸다. 클라이언트는 자기 잔액이 얼마인지 몰라도 되고, 실패하면 에러 코드로 알게 된다.
↓ C2Z C2ZMailBuy → Gateway 릴레이 → World 라우팅 → Zone의 LB → PostToBasic(zoneId)
BASIC 스레드 (ZoneInstance::HandleMailBuy)
ZoneUnitOfWork를 먼저 스택에 만든다
파싱 실패도 "이 요청의 결말"이라 클라이언트에는 같은 경로(Z2CTaskResult)로 에러가 돌아가야 한다 — 그래서 파싱보다 UnitOfWork를 먼저 연다. 이 시점에 Common::RequestIdGenerator가 요청 id(밀리초 41 + 노드 8 + 시퀀스 14비트)를 하나 발급한다.
↓ ① 우편을 먼저 넣는다
같은 BASIC 스레드
player.GetMailBox()->Write()->AddMail(info, uow)
Write()는 Thread::Mutexed의 unique_lock 진입점이다(우편함은 만료 스윕이 다른 스레드에서 돌기 때문에 감싸져 있다). 성공하면 mails_에 넣고 AddMailTask를 UnitOfWork에 기록한다 — 상태를 바꾼 뒤에만 기록하므로 태스크 목록이 곧 "실제로 적용된 변경"이 된다.
↓ ② 골드를 나중에 깎는다
같은 BASIC 스레드
player.GetWallet().DecCurrency(Gold, 100, uow)
지갑은 Mutexed로 감싸지 않는다 — 이 모델을 건드리는 건 그 존의 BASIC 스레드뿐이라 락이 필요 없다("전부 락"도 "전부 무락"도 아니고 모델마다 실제 접근 스레드 수에 맞춘다). 값을 바꾸는 통로는 SetTracked 하나뿐이라 검증 → 이전 값 포착 → 태스크 기록 → 대입이 한 자리에서 일어난다. 기록되는 CurrencyTask는 새 값과 이전 값을 둘 다 싣는다.
↓ 핸들러가 return해 uow가 스코프를 벗어남
같은 BASIC 스레드
ZoneUnitOfWork::~ZoneUnitOfWork — 에러 없음 → 전송
태스크 2건을 한 번만 직렬화하고 같은 바이트를 두 곳으로 보낸다: World로 Z2WUnitOfWorkStream(playerId + requestId + 스트림), 그 클라이언트에게 Z2CTaskResult(errorCode + requestPacketId + requestId + 스트림).
↓ S2C Z2CTaskResult
ProtocolClient
[recv] TaskResult request=6 requestId=9086... tasks=2
- Mail Added mailId=1 title=선물
- Currency type=1 1000 -> 900

두 모델의 변경이 응답 하나로 돌아온다. 실제 클라이언트라면 우편함 목록에 한 건 추가하고 잔액 표시를 새 값으로 덮어쓴다 — 증감량을 누적하지 않으므로 통지가 하나 유실돼도 다음 값에서 자동으로 맞춰진다.

2. 실패 경로 — 잔액이 부족하면 이미 들어간 우편이 되돌아간다

ProtocolClient
mail buy 너무비싼거 롤백되어야함 3600 999999
↓ ① 우편은 성공한다 (mails_에 들어가고 AddMailTask가 기록됨)
BASIC 스레드
② DecCurrency가 NotEnoughCurrency를 반환
SetTracked가 새 값이 음수임을 보고 아무 상태도 바꾸지 않고 에러 코드를 반환한다. 0으로 깎지 않는다(부분 적용 금지) — 클라이언트는 "999999 썼다"로 알고 서버는 "1000 썼다"가 되면 그 순간부터 양쪽 상태가 갈린다. 호출부가 그 반환값을 uow.SetError(...)로 옮기고 즉시 return한다 (모델 함수는 [[nodiscard]]라 반환값을 무시하면 컴파일 경고가 난다).
↓ 스코프 종료 → 소멸자가 HasError()를 보고 롤백 분기
같은 BASIC 스레드
UnitOfWork::RollbackAll — 기록의 역순으로
나중에 일어난 변경부터 되돌려야 중간 상태를 거치지 않는다. 여기서는 골드가 기록되지 않았으므로 AddMailTask 하나만 남아 있고, 그 태스크의 Rollback()이 DelMail을 부른다 — 롤백 전용 함수를 모델마다 따로 만들지 않고 정상 함수를 그대로 재사용한다.

종류별 분기 switch가 없다. 각 태스크가 자기 역연산을 알고 있고 Rollback()이 순수 가상이라, 새 태스크를 추가하면서 롤백을 빼먹으면 컴파일이 안 된다(전에는 런타임에 로그만 남기고 조용히 안 되돌렸다).
↓ 롤백 끝 → 에러 코드만 전송 (World로는 아무것도 나가지 않음)
ProtocolClient
[recv] TaskResult 실패 request=6 requestId=9086... error=200
태스크가 0건이다 — 되돌렸으므로 클라이언트가 적용할 변경이 없다. 그 뒤 mail add를 보내면 mailId가 하나 건너뛴 값으로 돌아오는데(3이 아니라 4), 롤백된 우편이 태운 번호다. nextMailId_를 되돌리지 않는 이유: id는 단조 증가만 하면 되고, 되돌렸다가는 이미 World로 나간 다른 태스크의 id와 겹칠 수 있다.

3. 롤백이 자기 자신을 다시 기록하지 않게 하는 장치

잘못된 방식
원래 UnitOfWork를 그대로 넘긴다
DelMail(mailId, uow)는 정상 함수라 DelMailTask를 또 기록한다. 그러면 (1) "지급하지 않았는데 삭제했다"는 태스크가 DB로 나가고 (2) 지금 순회 중인 목록에 원소가 추가돼 반복자가 깨진다.
실제 방식
Task::RollbackUnitOfWork를 넘긴다
전송 기능이 없는 UnitOfWork다 — 소멸자가 아무것도 하지 않으므로 롤백 중 쌓인 태스크가 조용히 버려진다. 덕분에 모델 함수를 한 벌만 유지하면 된다(롤백 전용 Undo* 함수를 필드마다 만들지 않는다).
핵심 불변식 / 주의
① 순서가 의미를 만든다 — 우편을 먼저 넣고 골드를 나중에 깎는 순서라서 롤백이 실제로 필요해진다. 반대 순서면 골드 검증이 먼저 실패해 되돌릴 것이 없다.
② 롤백은 실패할 수 없다는 전제 — 조금 전에 성공한 변경을 되돌리는 것뿐이라 검증에 걸릴 이유가 없다. 그래서 "롤백 실패 처리" 경로를 만들지 않고, 반환값이 Success가 아니면 불변식이 깨졌다는 신호로 보고 LOG.Error만 남긴다(복구를 시도하지 않는다). 이 전제를 지키려면 롤백 경로가 새 검증을 추가하지 않아야 한다.
③ DB는 Fire-and-Forget — 메모리에서 성공하면 DB도 성공으로 간주하고 응답을 기다리지 않는다. 그 대가로 DB 저장이 실패하면 그 변경이 조용히 유실되므로, DB 실패를 즉시 알아채는 로그·알럿이 이 정책의 짝이다.
④ 태스크에 새 값과 이전 값을 둘 다 싣는 이유 — 클라이언트는 새 값으로 덮어쓰고(유실에 강함), 롤백은 이전 값을 쓴다. "차감의 반대인 증가"를 부르는 역연산 방식은 요청한 양과 실제 바뀐 양이 다를 때(상한·하한에 걸린 경우) 틀린다.
