asio-server 플로우차트

기능이 실제로 어떻게 동작하는지 한눈에 보기 위한 HTML 다이어그램 모음. 새 기능을 추가할 때마다 여기에 한 페이지씩 늘어난다 (규칙은 README.md 참고). 전부 오프라인에서 그대로 열린다 — 외부 리소스(CDN 등) 의존 없음.

  • ProtocolClient → Gateway → World → Zone: Echo / Move / Chat 흐름
    클라이언트 패킷이 GatewayServer(순수 릴레이) → WorldServer(I/O 스레드는 PostTask만, 라우팅은 WorldWorker 단일 스레드) → ZoneServer(NETWORK → LB → BASIC → BROADCAST 풀 이동: Echo는 LB에서 즉시 응답 / Move·Chat은 zoneId sticky BASIC에서 처리 후 BROADCAST 풀에 스냅샷 위임)를 거쳐 다시 클라이언트로 돌아오는 전체 경로.
  • 존 경계 핸드오프 · Mail/UnitOfWork · 전체 브로드캐스트
    인접한 존 2개 사이의 재접속 없는 핸드오프(World 라우팅 테이블 교체만 — Gateway는 아예 모르고, 클라이언트는 Z2CEnterZoneNotify 한 장을 받는다), Zone::ZoneUnitOfWork(Task::UnitOfWork 파생)가 변경을 모았다가 Commit()에서 WorldServer DB 워커와 클라이언트 양쪽으로 보내고 실패 시 역순 롤백하는 흐름, Thread::Mutexed가 실제로 방어하는 지점(유지보수 타이머 vs 존 BASIC 스레드), WorldServer가 Zone 없이 직접 하는 전체 브로드캐스트까지.
  • 운영툴(GmTool) → World ToolProcessor: 공지 · 우편 · 쿠폰 흐름
    ASP.NET Core 운영툴이 WorldServer의 전용 포트(9300)에 붙어 ToolHello로 인증한 뒤 공지/우편/쿠폰 명령을 보내고, World의 ToolProcessor(다른 두 링크 핸들러와 동일한 "I/O 스레드는 복사만, 로직은 WorldWorker" 규약)가 처리하는 경로. 우편은 새 운영 전용 패킷이 아니라 기존 MailAdd/MailDel을 ClientEnvelopeHeader로 감싸 존에 주입하므로 존/UnitOfWork/DB 경로가 평소와 동일하게 흐른다. 대량 쿠폰 발급의 캠페인 네임스페이스 · 로컬 메모리 중복 검사 · 스풀 파일 fsync · 청크 벌크 인서트, 그리고 등록 시 체크 문자로 DB 앞단에서 99.9%를 거르는 흐름까지.
  • VisualClient: 화면 갱신 경로와 쿠폰 등록(소켓 ≠ HTTP) 흐름
    MonoGame 시각 클라이언트 쪽의 스레드 경계(소켓 수신 Task는 프레이밍 + 큐 적재만, 상태 변경은 게임 스레드 전용이라 WorldModel에 락이 없다 — 서버 ZoneInstance와 같은 이유)와, 통신 경로가 두 갈래로 갈라지는 지점. 이동·채팅· 우편·Echo는 전부 Gateway 소켓으로 가지만 쿠폰 등록만 GmTool.Web HTTP로 나가고, 그 보상은 응답이 아니라 T2WMailSendRequest → 존 → Z2CTaskResult 경로로 소켓으로 돌아온다. 우편 목록 조회 패킷 없이 UnitOfWork 스트림만으로 서버와 상태를 맞추는 방식, 존 핸드오프 때 우편함이 초기화되는 이유, 방향(dir) 필드가 서버에 없어 클라이언트가 좌표 변화량으로 만들어내는 것까지.
