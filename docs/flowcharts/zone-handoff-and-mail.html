존 경계를 넘을 때, 메일을 보낼 때, 전체 공지를 보낼 때

분산 게임 서버 구조를 단순화해 이식한 네 가지 흐름을 한 페이지에 모았다: (1) 존 1(x:[0,10))과 존 2(x:[10,20)) 사이의 재접속 없는 핸드오프 (ZoneServer.exe 1,2에서는 한 프로세스가 두 존을 같이 호스팅하고, 존을 가르는 건 프로세스가 아니라 zoneId % basicThreadCount sticky 라우팅이다 — 존 배치는 2×2 격자(1 2 / 3 4)이고 아래쪽 행은 ZoneServer.exe 3,4가 담당하므로, 세로로 넘는 이동(1↔3, 2↔4)이 프로세스를 넘는 핸드오프다), (2) Task::UnitOfWork Unit-of-Work(성공하면 DB와 클라이언트 양쪽으로 같은 태스크 목록, 실패하면 역순 롤백)와 Z2CTaskResult 왕복 확인, (3) Threading::Synchronized가 실제로 방어 역할을 하는 지점, (4) WorldServer가 Zone을 거치지 않고 직접 하는 전체 브로드캐스트. 기본 패킷 왕복 경로와 ZoneServer의 5-풀(NETWORK/LB/BASIC/TICK/BROADCAST) 구조는 Echo/Move/Chat 다이어그램 참고.

● ProtocolClient / 서버 콘솔 REPL (서버 워커 밖의 입력 주체) ● NETWORK / I/O 스레드 (asio strand — 바이트 복사·릴레이만) ● 워커 스레드 (WorldWorker / LB / BASIC / DB 워커 / 유지보수 타이머)

1. 존 경계 핸드오프 — 재접속 없이 라우팅 테이블만 교체

ProtocolClient
move 12 4 (Zone 1의 구간 x:[0,10)을 벗어남)
클라이언트는 여느 Move 패킷과 똑같이 보낼 뿐, 자신이 존 경계에 있다는 것도 알 필요가 없다.
↓ (Gateway → World의 WorldWorker → Zone의 NETWORK → LB를 거쳐 BASIC에 도착)
BASIC 스레드 (Zone 0, zoneId % basicThreadCount sticky)
ZoneInstance::HandleMove — 경계 검사
move.x < xMin_ || move.x >= xMax_이면 좌표를 갱신하는 대신 로컬 players_에서 즉시 지우고(그리고 MailRegistry::Remove도 같이) RequestZoneTransfer를 호출한다. player는 players_의 값이라 erase 이후엔 댕글링이 되므로, clientSessionId/playerId를 erase 전에 복사해둔다.
↓ Z2W Z2WZoneTransferRequest{zoneId, clientSessionId, playerId, x, y}
I/O 스레드 (WorldServer, Session의 strand)
ZoneLinkHandler::OnPacket — 복사 후 PostTask만
패킷 종류로 분기하지도, 레지스트리를 조회하지도 않는다. payload를 std::vector<byte>로 복사해 worldWorker_.PostTask(...)로 넘기는 게 전부다 -- 이 페이지에 나오는 World 쪽 로직은 전부 다음 단계(WorldWorker)에서 일어난다.
↓ PostTask (스레드 경계)
WorldWorker (World의 단일 처리 스레드)
ZoneLinkHandler::HandleZoneTransferRequest
ZoneLinkRegistry::FindZoneContainingX(x)로 대상 존(zoneId=1)을 찾고, ClientRegistry::SetZone으로 라우팅 테이블만 교체한다 (두 레지스트리는 이 스레드 하나만 건드리므로 락이 없다). World는 Gateway에 아무 것도 알리지 않는다 -- Gateway는 존 이동을 전혀 인지하지 못한다. 클라이언트에게도 World가 직접 알리는 건 없고, 아래에서 대상 존이 보내는 Z2CEnterZoneNotify 한 장만 도착한다(재접속·재인증 없음).
↓ W2Z W2ZEnterZoneRequest (zoneId만 대상 존으로 덮어쓰고 좌표는 그대로)
BASIC 스레드 (Zone 1, LB 스레드가 PostToBasic(zoneId=1)로 넘긴 뒤)
ZoneInstance::OnPlayerEnter
Zone 1이 이 플레이어를 새로 만들고(빈 우편함으로 시작 -- Mail은 zone-local이라 핸드오프 시 초기화되는 게 이 프로젝트의 알려진 단순화다) Z2CEnterZoneNotify를 되돌려 보낸다. 클라이언트 입장에서는 재접속 없이 [recv] Z2CEnterZoneNotify playerId=N zoneId=1만 새로 받을 뿐이다 -- 그래서 Gateway에게는 완전히 투명하지만, 클라이언트에게는 투명하지 않다(알림 한 장을 받는다).
알려진 단순화 — 핸드오프가 실패하면 플레이어가 유실된다: HandleMove는 대상 존을 확인하기 전에 로컬 players_/MailRegistry에서 먼저 지운다. 그래서 move -5 4처럼 x가 등록된 전체 존 구간(현재 0~20) 밖이면: Zone 0이 플레이어를 지우고 → World의 FindZoneContainingX(-5)가 std::nullopt → "핸드오프 대상 존을 찾지 못함" 경고 로그만 남기고 return → ClientRegistry의 zoneId는 여전히 0이라 이후 패킷은 Zone 0으로 계속 라우팅되지만 players_에 없으므로 ZoneInstance::HandleClientPacket이 전부 버린다. 즉 재접속하기 전까지 플레이어가 영구 유실된다 -- 실서비스라면 대상 존 확인 후 지우거나 실패 시 롤백해야 하지만, 여기서는 흐름을 단순하게 보여주려고 일부러 남겨둔 지점이다.

2. Mail Add/Del — Task::UnitOfWork(범용 Unit-of-Work)가 변경을 모았다가 Commit()에서 한 번에 전송, 실패하면 역순 롤백

BASIC 스레드 (해당 존, ZoneInstance::HandleMailAdd)
Zone::ZoneUnitOfWork + mailModel->Write()->AddMail
Zone::ZoneUnitOfWork(Core의 범용 Task::UnitOfWork를 상속해 "전송/역연산"만 콘텐츠가 채운 것)를 스택에 만든 뒤 mailModel->Write()->AddMail(info, unitOfWork) 호출 (Write()는 Threading::Synchronized의 unique_lock 진입점). MailModel::AddMail은 mails_를 갱신하며 unitOfWork.RecordTask(kind, payload)로 "무엇이 바뀌었는지"만 기록하고, 실패하면 unitOfWork.SetError(...)만 남긴다 -- 성공/실패 어느 쪽이든 아직 아무것도 네트워크로 전송하지 않는다.
↓ 핸들러 마지막 줄 unitOfWork.Commit()
같은 BASIC 스레드
Task::UnitOfWork::Commit → ZoneUnitOfWork::OnFlush
에러가 없으면 대상별로 ownerId + taskCount + {kind, payloadLen, payload}...로 직렬화해서 Db 대상은 playerId를 앞에 붙여 Z2W Z2WUnitOfWorkStream으로, Client 대상은 같은 목록을 Z2CTaskResult로 그 클라이언트에게 보낸다(전송 자체는 Session의 strand가 직렬화해주므로 어느 스레드에서 호출해도 안전하다).

에러가 있으면 기록해둔 태스크를 역순으로 되짚어 OnRollback이 역연산(Added↔Removed)을 부르고, 클라이언트에는 에러 코드만 간다 -- DB로는 아무것도 나가지 않는다. 내보내기를 소멸자가 아니라 Commit()에서 하는 이유: 기반 클래스 소멸자가 도는 시점에는 파생 부분이 이미 파괴돼서 가상 함수가 파생 구현으로 불리지 않는다(소멸자는 "Commit 없이 소멸"을 잡는 안전망만 맡는다).
↓ Z2W Z2WUnitOfWorkStream (World의 I/O 스레드는 복사 후 PostTask만)
WorldWorker (World의 단일 처리 스레드)
ZoneLinkHandler::HandleUnitOfWorkStream
앞의 playerId를 읽고 남은 바이트를 복사한 뒤, 그 안의 ownerId(=clientSessionId)로 해시해 Thread::AffinityWorkerPool<Db::DbWorker>(Core의 기존 owner-hash 워커 풀 재사용)의 고정된 워커로 넘긴다.
↓ PostTask (owner-hash로 고정된 워커)
DB 워커 스레드 (dbWorkers_.GetWorker(ownerId))
제너릭 태스크 목록을 kind별로 순서대로 처리
같은 플레이어의 태스크는 항상 같은 DB 워커에서 순서대로 처리되어 락이 필요 없다. 각 태스크는 // TODO: 실제로는 여기서 DB에 INSERT/DELETE 쿼리를 실행한다 주석과 함께 Debug 레벨 로그만 남긴다(부하 테스트 시 로그 I/O가 병목이 되는 걸 피하려고 Info가 아니라 Debug로 낮춰뒀다).

2-1. Z2CTaskResult — 서버가 DB에 남기는 목록과 클라이언트가 적용하는 목록이 같다

ProtocolClient / StressClient
mail add ... 전송
서버가 실제로 어떤 mailId를 배정했는지는 클라이언트가 알 방법이 없다 — 그래서 C2ZMailDel로 "자기가 만든 그 메일"을 정확히 지정해 지우려면 결과가 반드시 돌아와야 한다(부하 테스트가 id 불일치를 검증하려는 지점이기도 하다).
↓ C2Z C2ZMailAdd → ... → BASIC 스레드에서 처리
BASIC 스레드
ZoneInstance::HandleMailAdd → ZoneUnitOfWork::Commit()
핸들러는 ZoneUnitOfWork를 열고 모델을 부른 뒤 Commit()만 호출한다. 성공하면 같은 태스크 목록이 두 갈래로 나간다 — Db 대상은 World로(Z2WUnitOfWorkStream), Client 대상은 그 클라이언트에게(Z2CTaskResult). 실패하면 기록해둔 태스크를 역순으로 되짚어 메모리를 롤백하고 클라이언트에는 에러 코드만 간다(DB로는 아무것도 나가지 않는다).
↓ S2C Z2CTaskResult{errorCode, requestPacketId, 태스크 목록}
ProtocolClient / StressClient
[recv] TaskResult request=4 tasks=1 / - Mail Added mailId=N
클라이언트는 콘텐츠별 Ack 구조체를 파싱하는 대신, 받은 태스크 목록을 자기 메모리(우편함)에 그대로 적용한다 — 서버가 DB에 남기는 변경과 같은 목록이라 한쪽만 빠뜨릴 여지가 없다. 그 mailId로 C2ZMailDel을 보낸다.
↓ C2Z C2ZMailDel{mailId} → ... → BASIC 스레드
BASIC 스레드
ZoneInstance::HandleMailDel
같은 경로로 Removed 태스크가 돌아온다. 없는 mailId면 태스크 없이 errorCode=100(MailNotFound)만 온다 — 부하 테스트는 이 결과와 자신이 요청한 mailId가 일치하는지를 사이클마다 검증한다.

3. 메일 만료 삭제 — Synchronized가 실제로 방어하는 유일한 지점

별도 유지보수 스레드 (ZoneServerApp의 RepeatingTimer, ioPool_.Next()의 io_context에서 돎 — 존 워커 풀과 무관)
Mail::MailExpiryService::SweepOnce
MailRegistry::ForEach로 이 존의 모든 플레이어 Synchronized<MailModel>를 순회하며 mailModel->Write()(shared_mutex의 unique_lock)로 잠금을 잡은 뒤, TakeExpiredMailIds 조회와 DelMail(mailId, unitOfWork, isTimeout=true) 삭제를 같은 잠금 안에서 이어서 수행한다(그래서 임시 Write()가 아니라 named 프록시로 잠금을 유지한다).
↕ 동시에 발생할 수 있음
BASIC 스레드 (클라이언트의 mail del 요청 처리 중)
ZoneInstance::HandleMailDel → 같은 MailModel의 Write()
두 스레드가 같은 플레이어의 같은 MailModel 인스턴스를 동시에 건드릴 수 있는 이 프로젝트의 유일한 지점이다. Synchronized의 shared_mutex가 둘을 직렬화해주지 않으면 mails_ 맵이 동시 수정으로 깨질 수 있다 -- 나머지 게임 상태(players_의 PlayerState 등)는 항상 그 존의 BASIC 스레드 전용이라 락이 전혀 없는 것과 뚜렷이 대비된다.

4. 전체 공지 — World가 Zone을 거치지 않고 직접 브로드캐스트

WorldServer 콘솔 REPL 스레드 (수동 테스트용)
notice <메시지> 입력
main.cpp의 ConsoleLoop가 app.BroadcastToAll(Protocol::PacketId::W2CNotice, ...)를 호출한다 -- I/O 스레드도 워커도 아닌 제3의 생산자 스레드다.
↓ payload 복사 후 PostTask (스레드 경계)
WorldWorker (World의 단일 처리 스레드)
WorldServerApp::BroadcastToAll이 넘긴 태스크
ClientRegistry::ForEach로 Zone과 무관하게 현재 접속 중인 모든 clientSessionId를 순회하며 각각에게 ToClient envelope을 만들어 그 클라이언트가 물려있는 Gateway 세션으로 바로 전송한다. 콘솔 스레드가 clientRegistry_를 직접 순회하지 않고 여기로 넘기는 덕분에 "라우팅 테이블은 WorldWorker 전용"이라는 불변식이 유지된다.
↓ (Gateway가 그대로 벗겨서 전달)
ProtocolClient (여러 존에 흩어져 있어도 전부)
[recv] Notice(WorldServer 직접 브로드캐스트): ...
서로 다른 존(Zone 0 / Zone 1)에 있는 클라이언트도 동시에 받는다 -- Zone을 한 번도 거치지 않았다는 증거.
핵심 요약: 존 핸드오프는 World의 라우팅 테이블 교체만으로, 전체 브로드캐스트는 World의 클라이언트 레지스트리 직접 순회만으로 처리된다 -- 둘 다 Zone의 BASIC 스레드를 거의 건드리지 않고, 둘 다 WorldWorker 한 스레드에서 일어나므로 World 쪽에도 락이 없다. 반대로 Mail 상태 변경은 항상 그 존의 BASIC 스레드 (평소) 또는 별도 유지보수 스레드(만료 삭제)에서만 일어나고, 두 스레드가 만나는 유일한 지점만 Threading::Synchronized로 보호한다. 자세한 내용은 CLAUDE.md 참고.
