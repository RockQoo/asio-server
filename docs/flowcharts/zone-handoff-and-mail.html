존 경계를 넘을 때, 메일을 보낼 때, 전체 공지를 보낼 때

분산 게임 서버 구조를 단순화해 이식한 네 가지 흐름을 한 페이지에 모았다: (1) 존 서버 프로세스 2개(x:[0,10)/x:[10,20)) 사이의 재접속 없는 핸드오프, (2) Task::UnitOfWork Unit-of-Work + MailAddAck/MailDelAck 왕복 확인, (3) Threading::Synchronized가 실제로 방어 역할을 하는 지점, (4) WorldServer가 Zone을 거치지 않고 직접 하는 전체 브로드캐스트. 기본 패킷 왕복 경로는 Echo/Move/Chat 다이어그램 참고.

● TestClient (별도 프로세스) ● I/O 스레드 (릴레이/라우팅) ● 전용 로직 스레드 (TaskWorker / DB 워커 / 유지보수 타이머)

1. 존 경계 핸드오프 — 재접속 없이 라우팅 테이블만 교체

TestClient
move 12 4 (Zone 0의 구간 x:[0,10)을 벗어남)
클라이언트는 여느 Move 패킷과 똑같이 보낼 뿐, 자신이 존 경계에 있다는 것도 알 필요가 없다.
↓ (Gateway/World를 거쳐 ForwardToZone으로 도착)
로직 스레드 (Zone 0의 TaskWorker)
ZoneWorld::OnMove — 경계 검사
x < xMin_ || x >= xMax_이면 좌표를 갱신하는 대신 로컬 players_에서 즉시 지우고(그리고 MailRegistry::Remove도 같이) RequestZoneTransfer를 호출한다. 실패 시 플레이어가 유실될 수 있는 단순화지만, 존 2개 고정 인접 테이블이라 실제로 실패하지 않는다.
↓ Z2W ZoneTransferRequest{clientSessionId, playerId, x, y}
I/O 스레드 (WorldServer)
ZoneLinkHandler::HandleZoneTransferRequest
ZoneLinkRegistry::FindZoneContainingX(x)로 대상 존(zoneId=1)을 찾고, ClientRegistry::SetZone으로 라우팅 테이블만 교체한다. World는 Gateway에 아무 것도 알리지 않는다 -- Gateway는 존 이동을 전혀 인지하지 못한다. 클라이언트에게도 World가 직접 알리는 건 없고, 아래에서 대상 존이 보내는 EnterZoneNotify 한 장만 도착한다(재접속·재인증 없음).
↓ W2Z EnterZoneRequest (같은 좌표 그대로)
로직 스레드 (Zone 1의 TaskWorker)
ZoneWorld::OnPlayerEnter
Zone 1이 이 플레이어를 새로 만들고(빈 우편함으로 시작 -- Mail은 zone-local이라 핸드오프 시 초기화되는 게 이 프로젝트의 알려진 단순화다) EnterZoneNotify를 되돌려 보낸다. 클라이언트 입장에서는 재접속 없이 [recv] EnterZoneNotify zoneId=1만 새로 받을 뿐이다.

2. Mail Add/Del — Task::UnitOfWork(범용 Unit-of-Work)가 변경을 모았다가 한 번에 전송, Ack으로 왕복 확인

BASIC 스레드 (해당 존, ZoneWorld::HandleMailAdd)
Mail::MakeMailUnitOfWork + mailModel->Write()->AddMail
Task::UnitOfWork(Core 소유, 콘텐츠를 몰라도 되는 범용 클래스)를 스택에 만든 뒤 mailModel->Write()->AddMail(info, unitOfWork) 호출(Write()는 Threading::Synchronized의 unique_lock 진입점). MailModel::AddMail은 mails_를 갱신하며 unitOfWork.RecordTask(kind, payload)로 "무엇이 바뀌었는지"만 기록하고, 실제로 배정된 mailId를 반환한다 -- 아직 아무것도 네트워크로 전송하지 않는다.
↓ 함수 종료, unitOfWork가 스코프를 벗어남
Zone↔World 연결의 스레드 (호출한 스레드 그대로)
Task::UnitOfWork::~UnitOfWork
누적된 태스크가 있으면 그때서야 ownerId + taskCount + {kind, payloadLen, payload}...로 직렬화해 flush 콜백(MakeMailUnitOfWork가 만든 람다, playerId를 앞에 붙임)을 호출 → Z2W UnitOfWorkStream 한 번으로 전송한다 -- "패킷 처리 = 스택에 diff를 쌓았다가 함수 종료 시 자동 전송"하는 Unit-of-Work 패턴이다.
↓ Z2W UnitOfWorkStream
WorldWorker (World의 단일 처리 스레드)
ZoneLinkHandler::HandleUnitOfWorkStream
제너릭 태스크 목록을 파싱해 ownerId(=clientSessionId)로 해시한 뒤 Thread::AffinityWorkerPool<Db::DbWorker>(Core의 기존 owner-hash 워커 풀 재사용)의 고정된 워커로 넘긴다 -- 같은 플레이어의 태스크는 항상 같은 DB 워커에서 순서대로 처리되어 락이 필요 없다. 각 태스크는 // TODO: 실제 DB INSERT/DELETE (Docker 연동 후 구현) 주석과 함께 Debug 레벨 로그만 남긴다(부하 테스트 시 로그 I/O가 병목이 되는 걸 피하려고 Info가 아니라 Debug로 낮춰뒀다).

2-1. MailAddAck / MailDelAck — 클라이언트가 자기 mailId를 확인할 수 있어야 한다

TestClient / LoadTestClient
mail add ... 전송
서버가 실제로 어떤 mailId를 배정했는지는 클라이언트가 알 방법이 없다 — 그래서 MailDel로 "자기가 만든 그 메일"을 정확히 지정해 지우려면 Ack이 반드시 있어야 한다(부하 테스트가 id 불일치를 검증하려는 지점이기도 하다).
↓ C2Z MailAdd → ... → BASIC 스레드에서 처리
BASIC 스레드
ZoneWorld::HandleMailAdd
AddMail이 반환한 mailId를 그대로 SendToPlayer(..., PacketId::MailAddAck, {mailId})로 즉시 되돌려준다.
↓ S2C MailAddAck{mailId}
TestClient / LoadTestClient
[recv] MailAddAck mailId=N
이 mailId로 MailDel을 보낸다.
↓ C2Z MailDel{mailId} → ... → BASIC 스레드
BASIC 스레드
ZoneWorld::HandleMailDel
DelMail이 반환한 성공 여부를 MailDelAck{mailId, success}로 되돌려준다. success=false는 그 mailId가 이미 없었다는 뜻 — 부하 테스트는 이 값과 자신이 요청한 mailId가 일치하는지를 사이클마다 검증한다.

3. 메일 만료 삭제 — Synchronized가 실제로 방어하는 유일한 지점

별도 유지보수 스레드 (ZoneServerApp의 RepeatingTimer, zone 워커와 무관한 io_context에서 돎)
Mail::MailExpiryService::SweepOnce
MailRegistry::ForEach로 이 존의 모든 플레이어 Synchronized<MailModel>를 순회하며 mailModel->Write()(shared_mutex의 unique_lock)로 만료 메일을 찾아 DelMail(mailId, unitOfWork, isTimeout=true)를 호출한다.
↕ 동시에 발생할 수 있음
로직 스레드 (TaskWorker, 클라이언트의 mail del 요청 처리 중)
ZoneWorld::OnMailDel → 같은 MailModel의 Write()
두 스레드가 같은 플레이어의 같은 MailModel 인스턴스를 동시에 건드릴 수 있는 이 프로젝트의 유일한 지점이다. Synchronized의 shared_mutex가 둘을 직렬화해주지 않으면 mails_ 맵이 동시 수정으로 깨질 수 있다 -- 나머지 게임 상태(PlayerState 등)는 항상 zone 로직 스레드 전용이라 락이 전혀 없는 것과 뚜렷이 대비된다.

4. 전체 공지 — World가 Zone을 거치지 않고 직접 브로드캐스트

WorldServer 콘솔 (수동 테스트용 REPL)
notice <메시지> 입력
main.cpp의 ConsoleLoop가 app.BroadcastToAll(PacketId::Notice, ...)를 호출한다.
↓
I/O 스레드 (WorldServer)
WorldServerApp::BroadcastToAll
ClientRegistry::ForEach로 Zone과 무관하게 현재 접속 중인 모든 clientSessionId를 순회하며 각각에게 ToClient envelope을 만들어 그 클라이언트가 물려있는 Gateway 세션으로 바로 전송한다 -- World가 전체 클라이언트 레지스트리를 직접 들고 있기 때문에 가능한 지름길이다.
↓ (Gateway가 그대로 벗겨서 전달)
TestClient (여러 존에 흩어져 있어도 전부)
[recv] Notice(WorldServer 직접 브로드캐스트): ...
서로 다른 존(Zone 0 / Zone 1)에 있는 클라이언트도 동시에 받는다 -- Zone을 한 번도 거치지 않았다는 증거.
핵심 요약: 존 핸드오프는 World의 라우팅 테이블 교체만으로, 전체 브로드캐스트는 World의 클라이언트 레지스트리 직접 순회만으로 처리된다 -- 둘 다 Zone의 게임 로직 스레드를 건드리지 않는다. 반대로 Mail 상태 변경은 항상 그 존의 로직 스레드 (평소) 또는 별도 유지보수 스레드(만료 삭제)에서만 일어나고, 두 스레드가 만나는 유일한 지점만 Threading::Synchronized로 보호한다. 자세한 내용은 CLAUDE.md 참고.
