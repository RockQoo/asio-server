VisualClient는 무엇을 어디서 받아 그리나

Tool/VisualClient는 MonoGame 창 하나에서 존 이동 · 채팅 · 우편 · 쿠폰을 전부 확인하는 시각 클라이언트다. 다른 다이어그램이 서버 안쪽의 스레드 경계를 다루는 것과 달리, 이 페이지는 클라이언트 쪽 스레드 경계와 두 갈래로 갈라지는 통신 경로를 다룬다 — 게임 기능은 전부 소켓 (Gateway 9000)으로 가지만, 쿠폰 등록만 HTTP(GmTool.Web 5270)로 나간다. 소스는 Src/Net/GameLink.cs, Src/Model/WorldModel.cs, Src/Net/CouponClient.cs, Src/VisualClientGame.cs다.

● 소켓 수신 Task (프레이밍 + 큐 적재만) ● 게임 스레드 (Update/Draw — 상태 소유, 락 없음) ● 서버 측 (Gateway / World / Zone / GmTool.Web)
클라이언트 쪽 스레드 규약이 서버의 NETWORK/LB 분리와 같은 모양이다: 소켓 수신 Task는 [bodySize:2][id:2][payload] 프레이밍만 풀어 ConcurrentQueue에 넣고 게임 상태는 전혀 만지지 않는다. 실제 상태 변경은 게임 스레드가 GameLink.Drain()으로 큐를 비우면서 한다 — 그래서 WorldModel에는 락이 하나도 없다. 서버의 ZoneInstance가 BASIC 스레드 전용이라 락이 없는 것과 정확히 같은 이유다.

1. 게임 기능(이동 · 채팅 · 우편 · Echo): 전부 소켓

게임 스레드 — Update()
입력 → 목표 좌표 갱신 → 50ms마다 C2ZMove
WASD/클릭으로 클라이언트가 들고 있는 목표 좌표를 바꾸고, 프레임마다 보내지 않고 MoveSendInterval(50ms) 주기로만 전송한다. 화면에는 목표 좌표(작은 주황 점)와 서버가 확정해 되돌려준 좌표(플레이어 원)를 둘 다 그린다 — 그 사이 간격이 곧 왕복 지연이고, 존 경계를 넘는 순간에는 핸드오프가 도는 동안 눈에 띄게 벌어진다.
↓ TCP (Gateway 9000) — 이후 서버 내부 경로는 Echo/Move/Chat 다이어그램과 동일
Gateway → World → Zone
Gateway가 봉투를 씌우고, Zone의 BASIC 스레드가 처리
클라이언트가 보내는 바이트는 ProtocolClient와 한 글자도 다르지 않다. 돌아오는 길에 Gateway가 ClientEnvelopeHeader를 벗겨내므로, 클라이언트에 도달하는 것은 항상 PacketHeader + 순수 페이로드다 — 그래서 VisualClient는 릴레이 봉투를 알 필요가 없고 C2Z/Z2C/W2C 대역만 선언한다.
↓ TCP
소켓 수신 Task — GameLink.ReceiveLoopAsync
프레이밍만 풀어 ConcurrentQueue에 적재
TCP는 경계를 보장하지 않으므로 "헤더 4바이트가 다 왔는지 → 본문이 다 왔는지"를 매번 확인하며 꺼낸다. bodySize가 상한(8192)을 넘으면 그 지점부터는 패킷 경계를 알 수 없으므로 버퍼를 비우고 연결을 끝낸다 — 계속 읽어봐야 쓰레기만 나온다.
↓ 큐 (스레드 경계 — 여기서 게임 스레드로 넘어간다)
게임 스레드 — WorldModel.Apply
패킷 종류별로 상태에 반영
Z2CMoveNotify / Z2CChatNotify
게임 스레드
플레이어 좌표 갱신 · 채팅 로그 추가
방향(dir) 필드는 서버에 아예 없다. 화면의 작대기 방향은 직전 좌표에서 새 좌표로의 변화량으로 클라이언트가 만들어낸 값이다 (RemotePlayer.ApplyMove). 채팅은 보낸 즉시 찍지 않고 왕복해 돌아온 것만 표시한다 — 서버를 실제로 거쳤는지가 화면에 그대로 드러나야 하기 때문이다.
Z2CEnterZoneNotify (신규 입장 / 핸드오프 전입)
게임 스레드
zoneId 갱신 + 우편함/플레이어 목록 비우기
같은 패킷이 두 가지 상황으로 온다. zoneId가 바뀌었으면 핸드오프이고, 이때 서버가 이전 존의 우편함을 통째로 버린다 (ZoneInstance::HandleMove의 mailRegistry_.Remove → 새 존에서 빈 MailModel 재생성). 그래서 클라이언트도 목록을 비우고 화면에 그 이유를 밝힌다 — 안 비우면 서버에 없는 우편을 보여주게 되고 삭제를 눌러도 MailNotFound만 돌아온다.
↓ 우편 계열은 별도 경로 — Z2CTaskResult
게임 스레드 — WorldModel.ApplyTaskResult
UnitOfWork 태스크 스트림을 자기 메모리에 그대로 적용
페이로드는 errorCode(4) + requestPacketId(2) + [스트림]이고, 스트림은 ownerId(8) + taskCount(2) + taskCount개의 {kind(2) + len(4) + payload}다. 길이 프리픽스가 있어서 모르는 kind는 통째로 건너뛸 수 있다 — 서버가 새 콘텐츠 태스크를 추가해도 이 클라이언트는 죽지 않고 나머지를 계속 적용한다. errorCode가 0이 아니면 서버가 이미 롤백했고 스트림도 비어 있으므로 알리기만 한다. requestPacketId가 0이면 요청 없이 서버가 만든 변경 (우편 만료 삭제)이다.

우편 목록을 조회하는 패킷은 프로토콜에 없다. 입장 시점에 서버 우편함도 비어 있으므로, 이 스트림만 순서대로 적용하면 서버와 같은 상태가 유지된다 — 이게 Unit-of-Work 스트림을 DB뿐 아니라 클라이언트에도 그대로 흘려주는 이유다.

2. 쿠폰 등록: 이것만 소켓이 아니라 HTTP

왜 패킷이 아닌가: 쿠폰 등록은 클라이언트 대면 패킷 대역(C2Z/C2W)에 아예 없다. 대신 쿠폰 체계 전체(캠페인 · 발급 배치 · 체크 문자 · 레이트 리밋 · 사용 처리 · 등록 시도 로그)가 SQL Server와 GmTool.Web에 이미 있고, /api/coupon/redeem 하나만 운영자 토큰 없이 열려 있다 — 게임 사용자가 직접 부르는 자리로 설계된 것이기 때문이다. 같은 일을 C++ 서버에 다시 만들려면 World에 DB 연동부터 새로 해야 한다 (Db::DbWorker는 현재 로그만 남긴다).
게임 스레드 — CouponPanel
쿠폰 번호 입력 → CouponClient.RedeemAsync
clientSessionId로는 Z2CEnterZoneNotify가 준 playerId를 그대로 넘긴다. 서버의 playerId는 static_cast<uint32_t>(clientSessionId)이고 SessionId는 1부터 증가하는 카운터라 상위 32비트가 0이어서 두 값이 같다 — 세션 id 발급 방식을 바꾸면 이 전제가 깨진다. 요청은 Task로 띄워두고 매 프레임 폴링한다(게임 스레드를 막지 않는다).
↓ HTTP POST /api/coupon/redeem (5270)
GmTool.Web — CouponRedeemService
레이트 리밋 → 형식 → 체크 문자 → 캠페인 → 사용 처리
비용이 싼 것부터 검사하므로 무작위 입력의 약 99.9%가 DB 커넥션을 쓰지 않고 걸러진다. 응답은 { success, message } 두 필드뿐이고 실패 사유를 세분화하지 않는다 — "이미 사용됨"/"만료됨"/"없는 번호"를 구분해주면 공격자가 유효 번호 범위를 좁히는 단서가 된다. 진짜 이유는 coupon_redeem_attempt 테이블에만 남는다.
↓ 성공 시 — 보상은 응답이 아니라 소켓으로 온다
GmTool → World(9300) → Zone
T2WMailSendRequest → 존에 우편 주입
World의 Tool::ToolProcessor가 이걸 기존 C2ZMailAdd로 바꿔 존에 주입하므로, 존/UnitOfWork/DB 경로가 평소와 완전히 같다(자세한 건 운영툴 다이어그램).
↓ Zone → World → Gateway → 클라이언트 (Z2CTaskResult)
게임 스레드
우편함에 보상 우편 한 통이 생긴다
즉 쿠폰 등록 성공 문구와 우편 도착 사이에 짧은 시차가 있는 게 정상이다 — 둘은 서로 다른 연결로 오기 때문이다. 화면에서 이 두 사건이 따로 보이는 것이 "쿠폰 보상이 결국 게임 서버를 거쳐 온다"는 사실을 그대로 드러낸다.
이 클라이언트가 메우고 있는 프로토콜 공백 2개 (서버를 고치지 않기로 했으니 클라이언트 쪽 우회다 — 제대로 고칠 자리는 서버다):

· 입장 시 플레이어 스냅샷이 없다. ZoneInstance::BroadcastToZone은 그 패킷을 처리하는 순간 players_에 있는 사람에게만 보내는데, "입장 시 존 안의 플레이어 목록"을 주는 패킷이 없다. 그래서 나중에 들어온 창은 이미 있던 플레이어가 움직일 때까지 그 존재를 알 수 없다 — 창 2개를 띄우고 한쪽을 가만히 두면 다른 쪽 화면에서 아예 안 보인다. 그래서 이동이 없어도 1초마다 좌표를 다시 보낸다 (PositionHeartbeatInterval).
· 퇴장 통지가 없다. 서버는 W2ZLeaveZoneNotify로 자기 상태에서만 지우고 남은 사람들에게 알리지 않는다. 위 하트비트가 끊긴 것으로 퇴장을 추정해 6초 뒤 목록에서 지운다(WorldModel.ForgetStalePlayers) — 안 지우면 접속을 끊은 창이 화면에 영원히 남는다.
이 클라이언트가 의도적으로 하지 않는 것:
· 한글 IME 입력 — MonoGame은 OS가 완성한 조합 문자를 받아오지 않는다. 입력칸은 ASCII만 받고, 한글 왕복 확인은 채팅 패널의 프리셋 버튼으로 한다 (한글 한 글자가 3바이트라, 서버가 문자열 길이를 문자 수로 착각하고 있으면 거기서 바로 깨져 보인다).
· SpriteFont / 콘텐츠 파이프라인 — 한글을 넣으려면 U+AC00~U+D7A3 (11172자)을 통째로 선언해야 해서 텍스처가 감당이 안 된다. 대신 실제로 쓰인 글자만 GDI+로 그때그때 구워 아틀라스에 채운다(Src/Text/GlyphAtlas.cs).
· 존 경계 좌표 수신 — Z2CEnterZoneNotify는 playerId와 zoneId만 준다. 화면의 존 격자는 서버 main.cpp의 ParseZoneList 규칙("각 존은 10칸 폭")을 클라이언트가 복제한 값이다(Src/Protocol/ZoneLayout.cs) — 한쪽만 고치면 화면의 경계와 실제 핸드오프 지점이 어긋난다.
