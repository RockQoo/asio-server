# 전투를 존 레인에 둔 이유

대상: `Server/ZoneServer/Src/Combat/`, `Handler/PlayerProcessor::HandleAttack`,
`Game/Instance`

---

## 전투가 처음 만드는 문제

로그인·이동·우편·재화는 전부 **요청–응답**이다. 누가 보내면 처리하고 끝이라, 메시지의 주인을
"보낸 사람"으로 잡으면 그 사람의 데이터는 자동으로 직렬화된다. 그래서 지금까지 존 서버의
플레이어 레인(`owner = clientSessionId`)에는 락이 하나도 없었다.

전투는 두 가지를 동시에 깬다.

1. **아무도 요청하지 않아도 서버가 혼자 시간을 굴린다** — HP 리젠, 사망 뒤 리스폰, 몬스터 AI.
2. **내가 만지는 데이터의 주인이 내가 아니다** — `C2ZAttack`은 내 세션으로 들어오는데 HP가
   깎이는 쪽은 남이다.

둘을 합치면 **틱과 패킷 핸들러가 같은 유닛의 HP를 동시에 만진다.** 이 문서가 정하는 것은
그 충돌을 무엇으로 막느냐다.

## 고를 수 있었던 것

| | A. 존 단위 | B. 플레이어 단위 | C. 도메인 분할(현행 다른 콘텐츠) |
|---|---|---|---|
| 배치 | 틱 + 전투 패킷 전부 `zoneId` | 패킷 `sessionId`, 틱 `zoneId` | 존 상태 `zoneId`, 개인 `sessionId` |
| 락 | **0개** | 유닛마다 필요 | 경계를 안 넘을 때만 0개 |
| 병렬성 | 존 하나 = 코어 하나 | 존 하나 = 코어 N개 | 중간 |
| 경계를 넘는 작업 | **없음** | 많음 | 드랍·경험치·사망 보상 |
| 버그 재현성 | 결정론적 | 타이밍 의존 | 경계에서 타이밍 의존 |

**A를 골랐다.** 동시 접속 규모가 큰 서버라면 B가 답이다 — 존 하나에 수백 명이 들어오면 존을
직렬화해서는 버티지 못하고, 대신 전투 스탯마다 `shared_mutex` 래퍼를 단다. 규모가 다르면 답도
다르다.

### A를 고른 근거 셋

1. **지금 스코프에서 경계를 넘을 일이 없다.** HP/MP/ATK/DEF에 근접·원거리뿐이고 **HP는 영속
   대상이 아니다**(존은 DB를 한 줄도 만지지 않는다). B/C가 지불하는 비용의 대가로 받을 것이
   없다.
2. **코어를 못 쓰는 게 아니다.** 존이 여러 개면 존마다 다른 strand라 코어는 다 쓴다. 한계는
   "존 하나의 초당 작업량"이지 서버 전체가 아니다.
3. **락 제거가 이 프로젝트의 주제다.** "락을 안 썼다"보다 **"샤딩 단위를 왜 그렇게 골랐나"**가
   설명할 가치가 있는 이야기이고, A는 그 선택을 한 줄로 드러낸다.

### C(도메인 분할)를 전투에 쓰지 않은 이유

우편·재화는 지금도 C다(개인 것은 플레이어 레인, 존 상태는 존 레인). 전투에 그대로 쓰면
**드랍·경험치를 붙이는 순간 무너진다**:

```
몬스터 처치 (zoneId strand)
  → 드랍 아이템을 인벤에 넣어야 함 (sessionId strand)
  → post 로 넘김 → 인벤이 꽉 차서 실패
  → 그런데 "몬스터 사망"은 이미 확정돼서 되돌릴 수 없음   ← 여기서 터진다
```

**`Task::UnitOfWork`는 strand 경계를 못 넘는다.** 한 트랜잭션으로 묶을 작업은 한 strand 안에서
시작하고 끝나야 하고, 다른 strand로 post한 순간 그건 이미 다른 시점이라 되돌릴 방법이 없다.
A는 전부 같은 strand라 나중에 드랍·경험치를 붙여도 UnitOfWork 하나로 묶인다.

## 실제로 바뀐 것은 한 줄

```cpp
// 다른 요청: 플레이어 레인에서 끝난다
void PlayerProcessor::HandleMove(const PlayerContext& context, const C2ZMove& packet)
{
    context.player.Move().Write()->RequestMove(packet.move.x, packet.move.y);
}

// 전투: 존 레인으로 한 번 더 넘긴다
void PlayerProcessor::HandleAttack(const PlayerContext& context, const C2ZAttack& packet)
{
    zoneWorkers_.PostToZone(zoneId, [=] { ...GetZoneInstance(zoneId).HandleAttack(sessionId, attack); });
}
```

이 한 줄 때문에 `Combat::Unit` · `UnitRegistry` · `Service` 전체에 뮤텍스가 하나도 없다.

### 왜 LB 레인에서 바로 존으로 보내지 않았나

이상적으로는 패킷이 도착한 자리(`WorldLinkHandler`)에서 바로 `owner = zoneId`로 던지는 게
홉이 하나 적다. 그런데 **그 자리는 zoneId를 모른다** — 봉투에 있는 것은 `clientSessionId`뿐이고,
zoneId는 `Player`가 들고 있으며 `PlayerRegistry`는 플레이어 레인 전용에 샤딩돼 있다.

`sessionId → zoneId` 전역 표를 따로 두면 LB에서 바로 갈 수 있지만, 그 표는 여러 레인이 같이
보므로 `Thread::Mutexed`가 된다. **락을 없애려고 옮기는 참에 디스패치 경로에 락을 하나
만드는 셈**이라 택하지 않았다. 홉 하나는 `Post` 한 번이고, 존 레인의 실측 대기 시간은
아래처럼 틱 주기에 한참 못 미친다.

## 갈아탈 지점

**존 strand의 큐 대기 시간이 틱 주기를 넘기 시작하면** A의 한계다. 그때는 B로 가거나 존을
더 잘게 쪼갠다. 지표는 이미 찍히고 있다(`Processor::Group`의 레인 통계, `intervals.stats_dump_ms`):

```
프로세서 통계 . Group : Zone, Processor : ZoneSpace, Calls : 3616,
               AvgWaitUs : 24, MaxWaitUs : 448, AvgWorkUs : 14, MaxWorkUs : 201
```

틱 주기가 100,000µs인데 최대 대기가 448µs다. 여유가 200배 이상이므로 지금은 A가 맞다.

## 같이 정한 것들

### HP는 존 경계를 넘으면 최대치로 돌아간다

유닛은 `Instance`가 소유하므로 존을 옮기면 새로 만들어진다. 세로 핸드오프(프로세스를 넘는
이동)에서는 `Zone::Player` 자체가 새로 만들어지므로 이어받을 값이 애초에 없다.

HP를 이어받게 하려면 `W2ZEnterZone` 본문에 전투 스탯을 실어야 하는데, 그러면 **World가 전투를
알게 된다.** 지금 구조는 `World : 전투 코드 0줄 / Zone : DB 접근 0줄`이고 그 대칭이 이 서버의
계층 분리를 가장 짧게 설명한다. HP가 영속 대상이 아닌 이상 그 대칭을 깰 이유가 없다고 봤다.

**대가는 분명하다**: 경계에서 도망치면 풀피가 된다. 전투 중 이탈을 막아야 하는 콘텐츠가
생기면 그때 "최근 피격 N초 안에는 핸드오프 보류"를 넣는 쪽이 맞고, 그건 World가 아니라 Zone이
판단할 수 있다.

### 투사체 비행 시간을 서버에 두지 않았다

활은 쏘지만 **서버는 명중을 즉시 확정한다.** 화살이 날아가는 것은 클라이언트가 그린다.

서버가 비행 시간을 갖는 순간 생기는 것은 연출이 아니라 **"아직 확정되지 않은 데미지가 떠 있는
상태"**다. 그 상태가 생기면 답을 정해야 할 것이 줄줄이 따라온다 — 날아가는 중에 대상이 죽으면,
대상이 존을 나가면, 시전자가 접속을 끊으면, 틱이 밀려 여러 개가 한꺼번에 만료되면.

보이는 그림은 같다. 그래서 1차 구현은 즉발로 끝냈다. 다만 **나중에 붙일 자리는 비워 뒀다** —
명중 적용부(`Service::ApplyHit`)가 `Unit*`이 아니라 `UnitId`를 받고 매번 다시 찾는다. 즉발인
지금 그 재조회는 한 번도 실패하지 않지만, 예약 큐를 붙이는 순간 그 한 줄이 위 네 질문 중 셋의
답이 된다. 그리고 그 예약 큐는 **존 strand 전용이라 그냥 `std::vector`면 된다** — B로 갔다면
"패킷 스레드가 push, 틱 스레드가 erase"를 막을 뮤텍스가 하나 더 붙었을 자리다.

### 검증을 전부 통과한 뒤에 자원을 소모한다

`HandleAttack`은 사거리·생사·진영·쿨다운·MP를 모두 본 **뒤에** MP를 깎는다. 그래서 전투에는
롤백 코드가 없다. 시전 자원을 되돌리는 코드가 필요해지는 것은 시전 시간이 있을 때이고,
즉발만 있으면 "소모했는데 실패했다"가 만들어지지 않는다.

### 실패해도 반드시 응답한다

사거리 밖·쿨다운·MP 부족은 조작 중에 계속 나오는 **흔한 결과**지 예외가 아니다. 그래서
`Z2CAttackResult`는 어떤 경로로 끝나든 나가고, 사유는 `Protocol::EErrorCode`의 Combat 대역
(400~499)으로 구분한다. 전용 태그 enum을 따로 두지 않은 것은 클라이언트에 "에러를 읽는 방법"이
두 가지가 되기 때문이다.

### 상태 동기화는 틱 끝에 한 번, 사망은 즉시

공격 한 번마다 HP를 뿌리면 대규모 전투에서 브로드캐스트가 인원의 제곱으로 늘어난다. 그래서
값이 바뀐 유닛에 `dirty` 표시만 해두고 **틱 끝에 모아서 한 장**으로 보낸다.

예외가 둘이다. **시전자 응답**(`Z2CAttackResult`)은 요청의 답이라 미룰 수 없고,
**사망**(`Z2CUnitDead`)은 미루면 최대 한 틱 동안 이미 죽은 대상을 계속 때리게 된다.

### 유닛 id를 `uint32`로 두고 세션 id에서 잘라 만든다

플레이어 유닛의 id는 `clientSessionId`를 `uint32`로 자른 값이고, 그건 `Z2CMoveNotify`가
발신자를 싣는 방식과 **정확히 같다.** 그래서 클라이언트는 "움직이는 원"과 "HP 바"를 키 하나로
잇고, 변환표를 들고 있지 않아도 된다. 몬스터는 최상위 비트를 세운 대역(`kMonsterUnitIdBase`)을
써서 겹치지 않는다.

`mailId`를 `uint32`로 뒀다가 충돌할 뻔한 것과는 다른 상황이다 — 그건 DB에 영구히 쌓이는 PK였고,
유닛 id는 **존 메모리 안에서만 살고 존을 옮기면 버려진다.**
