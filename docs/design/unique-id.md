# RUID — 모든 id를 서버가 발급한다

대상 코드: `Shared/Core/Src/Common/RUID.h`

## 구조

```
RUID = [ 밀리초 41비트 ][ 노드 8비트 ][ 시퀀스 14비트 ]   (int64)
```

`requestId`뿐 아니라 `mailId`/`playerId`도 이 생성기가 발급한다 — 그래서 이름을 용도에서
떼어냈다(예전 이름은 `RequestId`).

## 왜 DB IDENTITY를 안 쓰나

서버가 메모리에서 먼저 확정하고 클라이언트에 응답한 뒤 DB에 반영하는 구조(UnitOfWork)라,
**DB가 id를 정하면 그 응답에 담을 id가 없다.**

## 왜 랜덤 GUID가 아닌가

클러스터드 인덱스 페이지 분할 때문이다. 시간순으로 커지는 키는 삽입이 항상 인덱스 뒤쪽에
붙지만, 무작위 키는 가운데에 끼어들어 페이지를 쪼갠다.

## 노드 번호는 대역으로 못박는다

| 대역 | 용도 |
|------|------|
| 0 | 예약 |
| 1~99 | World |
| 100~199 | Zone |
| 254 | 시드 |
| 255 | 운영툴 |

**프로세스마다 달라야 하고, 겹치면 서로 같은 id를 발급한다.** 예전처럼 World가 0, Zone이
zoneId를 쓰면 World를 한 대 늘리는 순간 겹친다.

## 실측 — "append-only"는 조건부로만 참이다

500만 개(5프로세스 × 10스레드): 중복 0건, 노드 배정 정확, DB 레인 분배 12.49~12.51%(이상값 12.5%).

| 조건 | 논리 단편화 | 페이지 채움 |
|------|-------------|-------------|
| 단일 노드 | 0.428% | 99.94% |
| 5개 노드 동시 발급 | 98%대 | — |

**"시간순 키라 재배치가 없다"는 발급자가 하나일 때만 성립한다.** 여러 노드가 동시에
발급하면 각 노드의 시퀀스가 서로 끼어들어 논리 단편화가 오른다. 그래도 무작위 키
대조군보다 **페이지 수가 22% 적다**.

검증 스크립트: `Sql/unique_keys.sql`, `Sql/verify_unique_keys.sql`

## 세션 id를 키로 쓰지 않는 이유

재접속마다 바뀌어서 "같은 사람의 DB 작업이 같은 스레드로 간다"(owner 어피니티)가 깨진다.
