# 틱만 병렬로 돈다 — 그리고 그 스레드는 레인 밖이다

대상 코드: `Server/ZoneServer/Src/Unit/UnitContainer.cpp`(`Tick`),
`Server/ZoneServer/Src/Unit/Unit.cpp`(`Tick`)

## 한 줄 요약

이 저장소에서 **병렬로 도는 구간은 하나뿐**이다. 존의 유닛 전원을 한 번에 적분하는 자리다.

```cpp
std::for_each(std::execution::par, readiedUnits_.begin(), readiedUnits_.end(),
              [&context](Unit* unit) { /* 이동 적분 + 경계 판정 */ });
```

흐름 전체는 [이동과 통지 시퀀스](../sequences/move-broadcast.html)의 ⑩ 단계.

## 왜 여기만 병렬인가

**병렬화가 성립하는 조건이 여기서만 갖춰지기 때문**이지, 여기가 제일 무거워서가 아니다.

`readiedUnits_` 는 맵이 아니라 **락 없는 스냅샷**(`std::vector<Unit*>`)이다. BASIC 레인이
이번 틱 도중에 로스터를 바꿔도 이 벡터는 흔들리지 않는다 — 생명주기 변경은 BASIC 이
대기줄에 예약하고 `OnEndTick` 이 확정한다(지연 파괴).

맵을 직접 돌면 이게 전부 깨진다. 반복자가 무효화될 수 있어 구간을 나눌 수 없고,
나누려면 순회 내내 락을 잡아야 하는데 그러면 병렬의 의미가 없다.

**즉 병렬은 목적이 아니라 지연 파괴의 부산물이다.** 그래서 다른 레인에는 못 쓴다 —
거기엔 스냅샷이 없다.

## 왜 `std::execution::par` 인가

| | |
|---|---|
| 표준이다 | 컴파일러 전용 라이브러리에 묶이지 않는다. 이 저장소가 `3rd/` 에 벤더 코드를 하나(asio)만 두는 것과 같은 판단 |
| 코드가 한 줄이다 | 스레드 풀을 직접 만들면 수명·종료·예외 규약을 또 하나 관리해야 한다 |
| 레인과 섞이지 않는다 | 틱 레인이 blocking 으로 기다리므로, 병렬이 끝나기 전에 다음 틱이 들어오지 않는다 |

**직접 만든 스레드 풀을 쓰지 않은 이유가 마지막 줄이다.** 레인 위에 또 다른 비동기 실행을
얹으면 "이 유닛의 틱이 언제 끝났나"를 추적해야 하고, 그 답이 `OnEndTick` 시점을 정한다.
동기 호출이면 그 질문 자체가 없다.

## 대가 — 이 스레드는 레인 모델 밖이다

이 저장소의 불변식은 **"레인 하나 = 큐 하나 + 스레드 하나"** 인데, 여기는 예외다.
표준은 실행 주체를 규정하지 않고, 구현이 자기 스레드 풀을 쓴다.

그래서 이런 것들이 성립하지 않는다.

- **설정의 레인 스레드 수 합계가 곧 이 프로세스의 스레드 수가 아니다.** 부하를 볼 때
  스레드 수를 세는 표(`docs/index.html`)에 안 잡히는 스레드가 있다.
- **레인 통계에 안 잡힌다.** `PushCount`/`PendingCount` 는 레인 큐의 값이라, 병렬 구간
  안에서 무슨 일이 벌어지는지는 이 계측으로 안 보인다.
- **스레드 이름이 없다.** `Basic#3` 같은 이름으로 레인을 가르는 방식이 여기엔 안 통한다.

일부러 받아들인 예외이고, **되살릴 수 있는 형태로 남겨 둔다** — 순차로 되돌리는 것은
`std::execution::par` 를 지우는 것이 전부다.

## 예외가 새면 프로세스가 죽는다

병렬 알고리즘의 함수 객체에서 예외가 빠져나오면 표준이 `std::terminate` 를 부른다.
try/catch 로 감싸도 **그 바깥에서 잡을 수 없다.**

그래서 **유닛마다 개별로 막는다.** 이건 취향이 아니라 필수다 — 안 막으면 유닛 하나의
예외가 그 존이 아니라 **프로세스 전체**를 끝낸다.

```cpp
try { unit->Tick(context); }
catch (const std::exception& ex) { LOG.Error(...); }
catch (...)                      { LOG.Error(...); }
```

이것이 "고치다 모르면 사고 나는 것"이라 소스 주석에도 남아 있다.

## `par_unseq` 를 쓰지 않는 이유

`par_unseq` 는 벡터화까지 허용하는데, 그러면 함수 객체 안에서 **락을 잡거나 할당을 하면
안 된다**(벡터화된 실행은 한 스레드 안에서 호출을 뒤섞을 수 있어 교착한다).

유닛 틱은 둘 다 한다.

- `MoveModel` 은 `Mutexed` 라 적분할 때 쓰기 잠금을 잡는다
- 예외 경로에서 `LOG` 를 부르고, 그 안에서 문자열을 만든다
- 우편 만료가 걸리면 `ZoneUnitOfWork` 를 열어 RUID 를 발급한다

**조건을 하나라도 어기면 정의되지 않은 동작**이고 증상이 교착이라 재현이 어렵다.
`par` 는 이런 제약이 없다.

## 아직 재지 않은 것

**병렬이 실제로 이득인지 측정한 적이 없다.** 아래는 전부 미측정이다.

| 질문 | 왜 물어야 하나 |
|---|---|
| 유닛이 적을 때도 이득인가 | 작업 분배 비용이 고정으로 든다. 존에 몇 명 없으면 순차가 빠를 수 있다 |
| 실제로 스레드를 몇 개 쓰나 | 구현이 정한다. 레인 스레드와 코어를 다툴 수 있다 |
| 틱 지연의 분산이 어떻게 되나 | 평균이 줄어도 꼬리가 길어지면 박자가 흔들린 것이다 |

**손익 분기점이 있으면 그 아래에서는 순차로 떨어뜨리는 것이 맞다**(유닛 수로 분기).
지금 그렇게 하지 않은 것은 기준이 될 수치가 없기 때문이지, 필요 없다고 판단해서가 아니다.

측정 항목은 성능 백로그에 있다([개선 백로그](../performance.html#backlog)).
