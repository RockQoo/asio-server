# Group — 메시지 큐 + 레인 어피니티

대상 코드: `Server/Core/Src/Processor/Group.h`

## 한 줄 요약

큐 그룹 하나 = `asio::io_context` + 소비자 스레드 N개 + `strand` N개.
메시지에 **주인을 줄 수도 있고 안 줄 수도 있다**:

```
Post(프로세서, ownerId, work)   주인 있음 → strand[ownerId % N] 으로 직렬화
Post(프로세서, work)            주인 없음 → 남는 스레드가 집어간다
```

주인을 준 일은 **겹치지 않고 보낸 순서대로** 처리되므로 그 데이터에 락이 없다.

## 두 서버가 이걸 다르게 쓴다

| | 어떻게 쓰나 | 전역 데이터 |
|---|---|---|
| **Zone** | 전부 주인 지정(`clientSessionId` / `zoneId`) | 락이 거의 없다 |
| **World** | 기본은 주인 없음, 순서가 필요한 것만 지정 | `Mutexed`가 필요하다 |

World가 그런 이유는 하는 일이 대부분 **릴레이**라서다 — 짧고 순서가 중요한 것과, 전체
대상이라 주인이 없는 것이 섞여 있다. 자세한 건 [locking-strategy.md](locking-strategy.md).

## 메시지의 세 요소

| 요소 | 역할 |
|------|------|
| `ownerId` | **선택이다.** 주면 `strand[ownerId % N]`으로 직렬화되고, 안 주면 남는 스레드가 집어간다 |
| `processorId` | **스레드 배정에 관여하지 않는다.** 그 스레드에서 누구의 핸들러를 부르는지를 나타내는 태그이고, 계측과 로그에서 작업 종류를 가르는 데 쓴다. 그래서 한 그룹 안에 여러 프로세서(Main/Tool/…)가 스레드를 공유하며 공존한다 |
| 내용 | 프로세스 내부 전달이라 **직렬화하지 않는다.** 호출 가능 객체를 타입 그대로 옮긴다(직렬화는 프로세스 경계, 즉 패킷에서만 한다) |

## ownerId를 무엇으로 할지는 호출부가 정한다

기준은 **"이 메시지가 건드릴 데이터의 주인"** 이다 — 세션 작업이면 `sessionId`, 존 공간
상태를 만지면 `zoneId`, 길드 동기화면 `guildId`. 그래서 `Group`은 `ownerId`의
의미를 모르고 `uint64_t`로만 받는다.

## "같은 스레드"가 아니라 "직렬화"다

구현은 `asio::strand`다. strand가 보장하는 것은 셋이다 — **겹치지 않음 · 보낸 순서 · 앞
작업의 쓰기가 뒤 작업에 보임(happens-before)**. 매번 같은 스레드에서 도는 것은 보장하지
않는다: 같은 주인의 A·B·C가 각각 1번·3번·2번 스레드에서 돌 수 있다.

**락 없는 접근에 필요한 조건은 그 셋이고 스레드 정체성은 아니다.** 어피니티(`ownerId % N`으로
스레드를 고정)는 수단이었고 목적은 직렬화였는데, strand가 그 목적을 직접 준다. 덤으로 주인
없는 일을 같은 스레드 풀이 집어갈 수 있어서 한 레인만 뜨거워지는 편중이 사라진다.

대가는 하나 — **`thread_local`에 기대면 안 된다.** `DbConnectionPool`이 스레드당 커넥션을
두는 것은 여전히 유효하지만(커넥션 수 = 스레드 수), 커넥션에 세션 상태(임시 테이블, `SET`
옵션)를 남기고 다음 작업이 그걸 기대하면 깨진다.

### strand 개수는 지금 스레드 수와 같다

`ownerId % N`이라 **`% N`이 같은 남남끼리는 서로를 막는다** — 3번과 11번은 아무 관계가
없는데 11번의 긴 작업이 3번을 기다리게 한다. strand는 스레드와 무관한 개념이라 owner마다
하나씩 둘 수도 있고(strand 본체는 수십 바이트, 뮤텍스는 193개 풀을 공유한다), 그러면 이
간섭이 사라진다. 아직 그렇게 하지 않은 이유는 **바꾸기 전 부하 수치를 남겨두기 위해서**다.

## 함정 — 어피니티는 만능이 아니다

**한 메시지가 주인이 다른 데이터를 함께 만지면 이 보호가 깨진다.** 그때는 `ownerId`
어피니티(1층) 대신 모델 단위 읽기/쓰기 락(`Thread::Mutexed`, 2층)이 필요하다.
어피니티는 "대부분의 경합을 없애는" 장치이지 "모든 경합을 없애는" 장치가 아니다.

## ProcessorId concept이 요구하는 것

- `T::Count` — 통계를 프로세서별 배열 칸으로 잡아야 해서 마지막 원소로 개수가 필요하다
- 같은 네임스페이스의 ADL `ToString()` — 통계 덤프에 이름을 찍으려고

둘 다 `Log::LogCategoryType`과 같은 방식이다. **Core는 어떤 프로세서가 있는지 몰라야 하므로**
콘텐츠 계층(Gateway/World/Zone)이 각자 자기 enum을 정의한다.

## 통계를 스레드마다 따로 두는 이유

경합 제거가 목적이기도 하지만, 그보다 **어느 스레드에 일이 몰렸는지**를 보려는 것이다 —
`ownerId` 종류가 적으면 스레드 하나만 뜨겁고 나머지는 논다.

`LogStats()`의 핵심은 **처리 시간이 아니라 대기 시간**이다:

```
대기가 길고 CPU가 남는다   -> 스레드 부족. 늘리면 나아진다
대기가 길고 CPU가 꽉 찼다  -> 스레드를 늘려도 무의미. 로직이나 구조를 고쳐야 한다
```

처리 시간만 봐서는 이 둘이 구분되지 않는다. 스레드별로도 찍는 건 **편중**을 보려는 것이고,
그게 이 프로젝트가 겪은 병목의 모양이었다.

## 느린 작업 경고가 `ELogCategory::General`인 이유

이 헤더는 여러 프로젝트(Core/WorldServer/ZoneServer/…)에서 include되고 프로젝트마다 자기
`ELogCategory`를 따로 정의한다(`.claude/rules/cpp-patterns.md`). **전부가 공통으로 갖는
`General`이어야 어디서 include되든 컴파일된다** — `Thread::Mutexed`가 같은 이유로 General을
쓴다. WorldServer에서는 `ELogCategory::Thread`가 아예 `Thread` 네임스페이스로 해석돼 버린다.
