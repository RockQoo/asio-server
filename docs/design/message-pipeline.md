# 메시지 파이프라인 — 세 좌표와 레인

대상 코드: `Server/Core/Src/Pipeline/`
(`MessageProducer.h` · `MessageProcessor.h` · `Types.h` · `ILaneSet.h`)

## 한 줄 요약

보내는 쪽은 **세 좌표**만 준다. 받는 쪽 객체도, 어느 스레드인지도 몰라도 된다.

```cpp
PushMsg<EProducerType::Basic>(msgType, targetProcessorId, msgOwnerId, body);
//                            어느 함수  어느 객체          어느 스레드
```

| 좌표 | 정하는 것 | 누가 아는가 |
|---|---|---|
| `msgType` | 받는 쪽 핸들러 표의 키 | 보내는 쪽과 받는 쪽이 합의한 enum |
| `targetProcessorId` | 어느 객체 | **등록 순서로 정해지는 런타임 인덱스** — `AddProcessor` 가 돌려준다 |
| `msgOwnerId` | 어느 레인 | `LaneIndexOf` 하나가 정한다 |

셋이 **서로 독립이다.** 같은 함수를 다른 객체가 갖고 있을 수 있고, 같은 객체의 일이
주인에 따라 다른 레인으로 갈린다.

## 왜 세 개로 나눴나

하나로 합치면 그때마다 다른 것이 망가진다.

| 합치면 | 무슨 일이 | 
|---|---|
| 객체 = 스레드 | 접속자 수만큼 스레드가 필요해진다 |
| 함수 = 객체 | 같은 처리를 하는 객체를 여럿 둘 수 없다(존마다 하나씩이 안 된다) |
| 주인 = 객체 | 한 객체의 일이 전부 한 스레드로 직렬화된다 — **존 전체가 스레드 하나가 된다** |

마지막이 실제로 겪은 것이다. 주인을 객체(존)로 통일했더니 그 존의 모든 콘텐츠가
한 줄로 섰다.

## 주인이 레인을 정한다 — 정의는 한 곳뿐

```cpp
// Pipeline::Types.h
size_t LaneIndexOf(OwnerId owner, size_t laneCount, bool useHash);
```

같은 주인의 일은 **겹치지 않고 보낸 순서대로** 처리된다. 그래서 그 주인으로 갈리는
상태에는 락이 없다 — 어피니티가 곧 보호다.

**이 규칙의 정의가 여기 하나뿐이어야 한다.** 레인 밖에서 같은 규칙으로 샤딩하는 자료구조가
있다면 반드시 이 함수를 불러야 한다. 두 군데서 따로 계산하면 "같은 샤드인데 다른 레인"이
생기고, 그러면 락 없는 맵에 두 스레드가 동시에 들어간다 — **크래시가 아니라 조용히 깨진다.**

### 해시를 끄는 경우

| | 주인 값 | 해시 | 왜 |
|---|---|---|---|
| TICK | `1 .. 2N` (촘촘) | **끈다** | 레인이 `2N+1` 개라 나머지 연산이 **항등**이 된다. 존마다 1:1, 충돌 0 |
| 그 외 | playerId(RUID) · zoneId(1800번대) | 켠다 | 값이 드문드문해서 끄면 한쪽 레인으로 몰린다 |

TICK 의 레인 수가 `존 수 x 2 + 1` 인 것은 **주인 최대값보다 크게 잡아 모듈로를 항등으로
만들기 위해서**다. 존 하나가 주인을 둘 갖는 이유는 **박자와 잡일을 갈라두기 위해서**이고
(버프 정리 같은 것이 밀려도 틱이 안 흔들린다), `+1` 은 존에 매이지 않은 전역 메시지 자리다.

기동 때 이 배정을 한 줄씩 찍는다:

```
레인 배정 . Zone : 1, TickOwner : 1, TickLane : 1, OtherOwner : 2, OtherLane : 2
레인 배정 . Zone : 2, TickOwner : 3, TickLane : 3, OtherOwner : 4, OtherLane : 4
```

**이게 없으면 1:1 이 깨져도 못 찾는다.** 증상이 "좀 느리다" 뿐이기 때문이다.

## 주인을 무엇으로 할지 — 규칙이 하나 있다

**사람 하나에 묶이는 일의 주인은 로그인 전까지 `clientSessionId`, 이후에는 `playerId` 다.
서버를 가리지 않는다**(`CLAUDE.md` 불변 규칙 3).

세션 id 로 두면 재접속마다 주인이 바뀌어 같은 계정의 일이 다른 레인으로 흩어지고, 서버를
건너가는 메시지는 양쪽 주인이 달라서 **받는 쪽이 그 사람을 못 찾고 조용히 버린다.**
실제로 그래서 우편이 DB 에 안 들어간 적이 있다 — 클라이언트에는 결과가 내려가고 DB 에는
없는, 가장 되돌리기 어려운 상태였다.

**사람이 주인이 아닌 일은 이 규칙의 대상이 아니다.** 존의 박자(존 서수) · 팬아웃(`zoneId`) ·
링크 수신(링크 세션 id) · 만기(고정 상수)는 각자 자기 주인을 쓴다. 다만 **주인을 아예 안 주는
경로는 만들지 않는다** — 전역 작업도 고정 상수 하나로 몰아 한 레인에 직렬화한다.

## 레인을 굴리는 방식이 둘이다 (config 로 고른다)

| | 스레드↔레인 | 3번이 뜨겁고 5번이 놀 때 |
|---|---|---|
| `queue` | **1:1**. `Basic#3` 이 곧 3번 레인의 주인 | 5번 스레드는 그냥 논다 |
| `strand` | 묶이지 않음 | 5번 스레드가 3번 레인의 밀린 일을 집어간다 |

**어피니티 대 워크 스틸링**이고, 그게 인터페이스를 둔 이유다. 어느 쪽이 나은지는 재봐야
안다 — 그래서 둘 다 남기고 기동 로그와 측정 기록에 어느 쪽으로 쟀는지 남긴다.

`strand` 쪽의 대가 하나: **`Basic#3` 이 3번 레인을 뜻하지 않는다.** 스레드 이름으로 레인을
가르려면 `queue` 여야 한다.

## "같은 스레드"가 아니라 "직렬화"다

`strand` 백엔드가 보장하는 것은 셋이다 — **겹치지 않음 · 보낸 순서 · 앞 작업의 쓰기가 뒤
작업에 보임(happens-before)**. 매번 같은 스레드에서 도는 것은 보장하지 않는다.

**락 없는 접근에 필요한 조건은 그 셋이고 스레드 정체성은 아니다.** 대가는 하나 —
**`thread_local` 에 기대면 안 된다.** DB 커넥션을 스레드당 하나 두는 것은 여전히 유효하지만
(커넥션 수 = 스레드 수), 커넥션에 세션 상태를 남기고 다음 작업이 그걸 기대하면 깨진다.

## 함정 — 어피니티는 만능이 아니다

**한 메시지가 주인이 다른 데이터를 함께 만지면 이 보호가 깨진다.** 그때는 주인 어피니티가
아니라 모델 단위 락(`Thread::Mutexed`)이 필요하다. 어피니티는 "대부분의 경합을 없애는"
장치이지 "모든 경합을 없애는" 장치가 아니다.

관련: [모델마다 보호가 다른 기준](player-and-models.md) · [락 전략 네 가지](locking-strategy.md)

### 그리고 — 주인이 하나뿐이면 레인도 하나다

측정에서 드러난 것이라 여기 남긴다. World 가 받는 바이트의 1단 주인은 **"어느 연결로
왔나"**(링크 세션 id)다. 연결이 하나면 주인도 하나고, **레인 8개를 만들어도 1개만 돈다.**

```
레인 분포 . Producer : Basic, Lanes : 8,
            PerLane : 20,994,668 · 21,131,691 · 21,024,448 · 21,133,057
                    · 443,991,263     <-- 4번 레인 하나가 나머지 7개 합의 3배
                    · 21,141,546 · 21,011,274 · 21,024,689
```

**레인을 몇 개 만들었는가와 실제로 몇 개가 도는가는 다르다.** 주인 값의 가짓수가 상한이다.

## 관측 — 배정과 적체를 따로 본다

| 값 | 무엇을 말하나 |
|---|---|
| **레인별 배정 누적** (`PushCount`) | 주인이 **고르게 갈리는가**. 평소에 봐야 한다 |
| **레인별 대기 개수** (`PendingCount`) | **지금 막혔는가**. 막히고 나서야 0 이 아니게 된다 |

둘 다 있어야 한다. 대기 개수만 보면 **노는 레인이 있어도 0 으로 똑같이 보인다** —
밀린 게 없다는 것과 일이 안 온다는 것이 구분되지 않는다.

배정 누적은 `PushMsg` 에서 relaxed 로 센다. 통계라 순서 보장이 필요 없고, 여기에 동기화를
걸면 **재는 행위가 재려는 대상을 느리게 만든다.** 계수기마다 캐시 라인을 통째로 주는 것도
같은 이유다(거짓 공유).

**Release 에서도 켜 둔다.** 성능 문제는 Release 에서만 나타나는데 빌드로 끄면 정작 볼 때
못 본다. 운영에서 "어디가 밀렸나"를 볼 수단도 이것뿐이다.

## Core 가 콘텐츠를 모르는 방법

`msgType` 은 `uint32_t` 하나이고, `EProducerType` 만 Core 가 안다. **어떤 메시지가 있는지도,
어떤 프로세서가 있는지도 Core 는 모른다** — 각 서버가 자기 enum(`EZoneMsg` / `EWorldMsg`)을
정의하고 `Regist(msgType, &X::OnSomething)` 으로 표를 채운다.

표에 없는 msgType 이 오면 **버리고 경고를 남긴다.** 조용히 사라지면 "보냈는데 아무 일도
안 일어난다"가 되어 원인을 찾을 데가 없다.
