# 락 전략 — 네 가지를 상황별로 나눠 쓴다

대상 코드: `Shared/Core/Src/Thread/Mutexed.h`, `Server/WorldServer/Src/World/ClientRegistry.h`,
`Server/WorldServer/Src/World/ZoneLinkRegistry.h`

## 목적은 "락 없음"이 아니다

락을 없애는 게 목적이 아니라 **락이 필요한 지점을 세어서 줄이는 것**이 목적이다.
그래서 전략이 네 개고, 자리마다 다른 것을 쓴다.

| 전략 | 쓰는 자리 | 예 |
|------|-----------|-----|
| ① 레인 어피니티 | 주인이 분명한 데이터 | `Player`의 지갑, `Instance`의 로스터 |
| ② 샤딩 | 주인별로 나뉘지만 컨테이너를 공유해야 하는 것 | `ClientRegistry`, `PlayerRegistry` |
| ③ 스냅샷 전달 | 다른 레인이 읽어야 하는 것 | 브로드캐스트 대상 목록 |
| ④ 명시적 락(`Mutexed`) | 주인을 가로질러 접근하는 자리 | `ZoneLinkRegistry`, 우편함 |

## ② 샤딩 — 키가 안 겹쳐도 맵은 안전하지 않다

큐 그룹이 스레드 N개이고 메시지가 `ownerId % N`으로 배정되면, 어떤 주인의 항목은 항상
같은 스레드에서만 만져진다. **그런데 맵 하나를 공유하면 그것만으로 깨진다** — 서로 다른
주인을 다루는 스레드들이 같은 컨테이너에 삽입/삭제를 하게 되고, **키가 겹치지 않아도
rehash가 컨테이너 자체를 흔든다.**

그래서 스레드 수만큼 맵을 나누고 `ownerId % shardCount`로 고른다. 각 맵을 그 맵을 담당하는
스레드 하나만 건드리게 되어 락이 사라진다.

**나누는 규칙이 큐 그룹의 스레드 선택 규칙과 반드시 같아야 한다**(둘 다 `% N`).
그래서 생성자가 그룹의 스레드 수를 그대로 받는다.

### 대가 — 전체 순회를 한 스레드에서 할 수 없다

샤드마다 그 샤드를 소유한 스레드로 메시지를 하나씩 보내야 한다.
`ForEachInShard`가 그 용도다(`App::BroadcastToAll`).

## ④ 왜 ZoneLinkRegistry만 락이 필요한가

`ClientRegistry`는 `clientSessionId`로 샤딩해서 "그 항목을 만지는 스레드가 항상 하나"를
만들 수 있다. **이 테이블은 그게 안 된다** — 어느 클라이언트의 메시지를 처리하든
(= 어느 레인에서든) 그 클라이언트가 있는 존의 링크를 찾아야 하기 때문이다.

즉 **주인이 다른 데이터를 가로질러 읽는 자리**라, 어피니티(1층)로는 못 막고
모델 단위 읽기/쓰기 락(2층)이 필요하다. 쓰기는 존 서버가 붙고 끊길 때뿐이라 극히 드물고
읽기는 패킷마다 일어나므로 `shared_mutex` 기반 `Mutexed`가 정확히 맞는 도구다.

관련: [Group — 어피니티는 만능이 아니다](processor-group.md)

## Mutexed 사용법

콘텐츠 클래스는 보통 `using Mutexed = Thread::Mutexed<MyClass>;`를 자기 안에 선언해 두고
`MyClass::Mutexed`로 짧게 쓴다.

```cpp
ref->Foo()           // 읽기(shared_lock). 가장 흔한 경우라 기본 문법을 여기 배정했다
ref.Write()->Foo()   // 쓰기(unique_lock). 임시 프록시가 그 한 번의 호출 뒤 즉시 소멸하며 잠금도 풀린다
```

**여러 호출에 걸쳐 같은 잠금을 유지해야 하는 드문 경우**(만료 대상을 조회한 뒤 그 결과로
바로 삭제까지 이어가야 해서 사이에 다른 스레드가 끼어들면 안 되는 시퀀스)에는 프록시를
named 변수로 받는다 — 프록시가 그 변수의 수명 동안 살아 있으므로 잠금도 그만큼 유지된다.

```cpp
auto writer = ref.Write();   // Read()도 같은 이유로 쌍을 이룬다
```

## ZoneLinkRegistry는 존 배치 규칙을 모른다

각 존이 등록할 때 알려준 사각형만 보고 판단한다. 배치가 격자에서 CSV 기반 불규칙 배치로
바뀌어도 이 클래스는 그대로다. `FindZoneContaining`이 "이 좌표는 어느 존 담당인가"를
결정하는 유일한 지점이고, 존 몇 개짜리 테이블이라 선형 탐색으로 충분하다 —
존이 많아지면 격자 인덱스가 필요해진다.
