# 락 전략 — 자리마다 다른 것을 쓴다

대상 코드: `Server/Core/Src/Thread/Mutexed.h`, `Server/WorldServer/Src/World/PlayerManager.h`,
`Server/WorldServer/Src/World/ZoneLinkRegistry.h`, `Server/ZoneServer/Src/Unit/UnitContainer.h`

## 목적은 "락 없음"이 아니다

락을 없애는 게 목적이 아니라 **락이 필요한 지점을 세어서 줄이는 것**이 목적이다.
지금 쓰는 전략은 셋이고, 자리마다 다른 것을 쓴다.

| 전략 | 쓰는 자리 | 예 |
|------|-----------|-----|
| ① 레인 어피니티 | 주인이 분명한 데이터 | `Player`의 지갑, `Unit`의 `zoneId` |
| ② 스냅샷 전달 | 다른 레인이 읽어야 하는 것 | 틱이 도는 유닛 목록, 브로드캐스트 대상 목록 |
| ③ 명시적 락(`Mutexed`) | 주인을 가로질러 접근하는 자리 | `PlayerManager`, `ZoneLinkRegistry`, 우편함, 이동 |

①의 실체는 직렬화이지 "같은 스레드"가 아니다 — 그 구분과 대가는
[메시지 파이프라인](message-pipeline.md)에 있다.

## 버린 전략 — 샤딩

"맵을 스레드 수만큼 쪼개고 `ownerId % N`으로 고른다"는 방법이 있다. 한때 `PlayerManager`가
이랬고 지금은 쓰지 않는다. 버린 이유가 **다시 꺼내려 할 때 걸리는 조건**이라 남긴다.

**성립 조건은 "그 샤드는 그 번호 스레드만 만진다"이고, 이건 서버마다 참이 아니다.**
Zone은 모든 메시지가 주인을 가져서 성립하지만, World는 기본이 "남는 스레드"라 성립하지
않는다. 실제로 운영툴의 단일 대상 명령(우편 발송·삭제)이 운영툴 레인에서 남의 샤드를
읽고 있었다.

그리고 **키가 겹치지 않아도 맵은 안전하지 않다.** 서로 다른 주인을 다루는 스레드들이 같은
컨테이너에 삽입·삭제를 하면 **rehash가 컨테이너 자체를 흔든다** — 그래서 "주인이 안
겹치니까 괜찮다"는 추론이 통하지 않는다.

대가도 있었다. **전체 순회를 한 스레드에서 할 수 없어서** 전역 작업(공지, 전체 대상 우편,
접속자 목록)이 전부 샤드별 팬아웃을 떠안았다. ③으로 바꾸면서 읽기 락 하나로 순회가 되어
그 팬아웃(샤드별 메시지, 원자 카운터, 완료 콜백, 취합 버퍼)이 통째로 사라졌다.

## World의 두 테이블이 락인 이유

**World는 Zone과 스레드 모델이 다르다.** 전역 테이블은 **어느 레인에서든 읽힐 수 있고,
어피니티로는 지킬 수 없다.**

`ZoneLinkRegistry`는 처음부터 그랬다 — 어느 클라이언트의 메시지를 처리하든 그 클라이언트가
있는 존의 링크를 찾아야 하기 때문이다. **주인이 다른 데이터를 가로질러 읽는 자리**다.

쓰기는 접속·종료·존 이동뿐이고 읽기는 패킷마다 일어나므로, `shared_mutex` 기반 `Mutexed`가
두 테이블 모두에 맞는 도구다.

## Mutexed 사용법

콘텐츠 클래스는 보통 `using Mutexed = Thread::Mutexed<MyClass>;`를 자기 안에 선언해 두고
`MyClass::Mutexed`로 짧게 쓴다.

```cpp
ref->Foo()           // 읽기(shared_lock). 가장 흔한 경우라 기본 문법을 여기 배정했다
ref.Write()->Foo()   // 쓰기(unique_lock). 임시 프록시가 그 한 번의 호출 뒤 즉시 소멸하며 잠금도 풀린다
```

**여러 호출에 걸쳐 같은 잠금을 유지해야 하는 드문 경우**(만료 대상을 조회한 뒤 그 결과로
바로 삭제까지 이어가야 해서 사이에 다른 스레드가 끼어들면 안 되는 시퀀스)에는 프록시를
named 변수로 받는다 — 프록시가 그 변수의 수명 동안 살아 있으므로 잠금도 그만큼 유지된다.

```cpp
auto writer = ref.Write();   // Read()도 같은 이유로 쌍을 이룬다
```

## ZoneLinkRegistry는 존 배치 규칙을 모른다

각 존이 등록할 때 알려준 사각형만 보고 판단한다. 배치가 격자에서 CSV 기반 불규칙 배치로
바뀌어도 이 클래스는 그대로다. `FindZoneContaining`이 "이 좌표는 어느 존 담당인가"를
결정하는 유일한 지점이고, 존 몇 개짜리 테이블이라 선형 탐색으로 충분하다 —
존이 많아지면 격자 인덱스가 필요해진다.
