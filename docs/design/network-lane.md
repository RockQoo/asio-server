# 소켓 단계를 레인으로 만들지 않은 이유

대상: `Server/Core/Src/Pipeline/Types.h`(`EProducerType`), `Server/Core/Src/Network/Session.h`

이 서버는 메시지가 지나는 단계마다 레인(`MessageProducer`)을 하나씩 둔다 —
`Lb` / `Basic` / `Tick` / `Broadcast` / `Db` / `Timer`. 그런데 **소켓 단계만 레인이 아니다.**
일관성을 깨고 예외를 둔 자리라 근거를 여기 남긴다.

## 소켓 단계가 하는 일은 둘이다

| | 하는 일 |
|---|---|
| 수신 | 완료 통지를 받아 바이트를 모으고 프레임 경계로 자른다 |
| 송신 | 한 연결에 대한 쓰기를 **세션 단위로 직렬화**한다(두 스레드가 같은 소켓에 동시에 쓰면 프레임이 섞인다) |

레인으로 만든다면 수신은 전용 스레드가 완료를 받고, 송신은 `owner = sessionId`로 들어온
메시지를 소비자 스레드가 처리하는 모양이 된다.

## asio가 그 둘을 이미 한다

| 하는 일 | 레인으로 만들면 | asio |
|---|---|---|
| 수신 | 전용 스레드 + 완료 처리 | `io_context` + `async_read_some` |
| 송신 직렬화 | `owner = sessionId` 어피니티 | `Session::strand_` |

`strand`가 보장하는 것(비동시 실행 + 넣은 순서 유지)이 `owner = sessionId` 레인이 보장하는
것과 **같다.** 목적이 같은 장치가 이미 있는 자리다.

## 얹으면 이음매가 생긴다

문제는 성능이 아니라 **주인이 둘이 된다**는 것이다. 송신 큐(`sendQueue_`)의 주인이
`strand_`에서 레인으로 넘어가는데, asio는 자기 규약대로 계속 움직이므로 두 장치가 만나는
지점이 생긴다.

| 만나는 지점 | 무슨 일이 | 안 풀면 |
|---|---|---|
| `async_write` 완료 | asio가 자기 스레드에서 콜백을 부르는데, 다음 전송은 레인이 해야 한다 | 두 스레드가 같은 큐를 만진다. **크래시가 아니라 가끔 전송이 멈추는** 증상 |
| 연결 종료 | 수신은 asio 쪽, 송신은 레인 쪽에서 동시에 감지된다 | 소켓을 누가 닫을지가 안 정해진다 |

둘 다 풀 수 있다(완료를 다시 레인으로 되돌리고, 닫기를 한쪽으로 몬다). 다만 **빠뜨렸을 때
조용히 깨지는 종류**라, 얻는 것과 견줄 필요가 있었다.

## 얻는 것이 서버마다 다르다

`owner = sessionId`이므로 병렬도는 **그 프로세스에서 나가는 연결 수**가 상한이다.

| 나가는 연결 | 레인으로 얻는 병렬도 |
|---|---|
| Zone → World (1개) | **0** — 레인 하나 = strand 하나 |
| World → Zone (프로세스 수만큼) | 거의 0 |
| Gateway → 클라이언트 (동시 접속 수만큼) | **실제로 갈라진다** |

무거운 일인 프레임 생성은 **이미 호출한 레인에서 끝난다** — `Session::SendPacket`이
`BuildFrame`을 먼저 하고 그다음에 post하기 때문이다. 소켓 스레드로 넘어가는 것은 큐에 넣는
동작뿐이다. 그래서 서버 간 링크에서는 레인을 둬도 옮겨지는 부하가 거의 없다.

## 그래서 지금은 두지 않는다

`EProducerType`에 `Network` 값을 두지 않는다. 안 쓰는 enum 값이 남아 있으면 "만들다 만 것"과
구분이 안 되기 때문이다. 되살릴 때 값을 다시 추가하면 된다.

## 잃는 것과 메우는 방법

**송신 적체가 레인 통계에 안 잡힌다.** 레인은 큐 길이가 통계에 찍히지만 `sendQueue_`는
strand 안이라 밖에서 안 보인다. 부하 시험에서 "수신이 밀렸나 송신이 밀렸나"를 못 가른다.

→ 세션 송신 큐 깊이를 통계로 따로 노출해서 메운다. 레인을 두지 않아 실제로 잃는 것은
이것 하나였다.

**송신 스레드 수를 따로 못 준다.** 송신이 소켓 스레드에서 돌아 수신과 같은 스레드를 다툰다.
동시 접속이 큰 Gateway에서 먼저 드러날 값이라, 드러나면 그때 다시 본다.

## 되살린다면 — 측정 항목으로

레인 백엔드(`lane_backend = queue | strand`)를 둘 다 구현해 두고 설정으로 고르는 것과 같은
방식이 맞다. 소켓 단계도 **레인 경유 / strand 직행**을 설정으로 고르게 만들어 두면 위의
"얻는 것이 서버마다 다르다"를 추측이 아니라 수치로 말할 수 있다.

**지금 넣지 않는 이유가 하나 더 있다.** 레인을 두면 모든 패킷에 홉이 하나씩 붙는다. 지금
재려는 것이 따로 있는 상황(수신 단계 수, 레인 백엔드)에서 먼저 넣으면 차이가 무엇 때문인지
갈리지 않는다. **재려는 것을 다 재고 난 뒤에 이걸 재는 순서가 맞다.**
