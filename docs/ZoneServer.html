ZoneServer 게임 로직

플레이어와 존의 권위 상태를 들고 있는 서버. 이 프로젝트의 핵심이 전부 여기 있다.

한 줄 요약

프로세스 하나가 존 여러 개를 호스팅한다(ZoneServer.exe 1,2). World로 나가서 붙고(accept하지 않는다), 받은 패킷을 주인에 따라 다른 레인으로 보낸다.

레인 다섯 — 주인이 다르기 때문에 나뉜다

I/O 스레드 2개                                  존마다 World 링크 하나
      ↓  바이트만 복사
LB        (2)        owner = 링크 세션 id    봉투를 깐다. 여기서 주인을 알아낸다
BASIC     (8)        owner = playerId       판단하고 예약한다 · 입퇴장 · 우편 · 재화 · UnitOfWork
TICK      (존수×2+1) owner = 존 틱 주인      예약된 것을 실행한다 · 적분 · 경계 판정
BROADCAST (4)        owner = zoneId         모았다가 한 번에 보낸다
TIMER     (1)        owner = 고정 상수       만기만 판정하고 원래 레인으로 되돌린다
담당 존마다 처리기가 네 벌이다(LB·BASIC·TICK·BROADCAST). 넷이 같은 Zone 하나를 shared_ptr로 같이 보고, 처리기 자신은 데이터를 갖지 않는다 — 바뀌는 것은 전부 Zone 안에 있다. BASIC과 TICK을 나눈 것이 이 서버의 설계 핵심이다. 창구(BASIC)는 손님이 오는 대로 즉시 처리해야 하고, 박자(TICK)는 모두에게 같은 시간이 흘러야 한다. 한 스레드에서 하면 둘 다 망가진다 — 손님이 몰리면 박자가 멎고, 박자가 도는 동안 손님이 줄을 선다.

TICK만 해시를 끈다

주인이 1..2N으로 촘촘하고 레인이 2N+1개라, 나머지 연산이 항등이 되어 충돌이 0이다(존마다 1:1). 존 하나가 주인을 둘 갖는 이유는 박자와 잡일을 갈라두기 위해서다 — 버프 정리 같은 것이 밀려도 틱이 안 흔들린다. 0번 레인은 존에 매이지 않은 전역 메시지 자리로 비워 둔다.

나머지 레인은 해시를 켠다. playerId는 RUID라, zoneId는 1800번대까지 값이 드문드문해서, 끄면 나머지 연산이 한쪽 레인으로 몰린다.

이 수치는 설정 파일에서 온다

스레드 수·포트·주기는 config/zone.cfg에서 읽는다. 값이 틀리면 기본값으로 넘어가지 않고 기동을 멈추고, 아무도 읽지 않은 키는 경고로 남는다(오타를 잡는 유일한 수단). TICK만 설정에 없다 — 담당 존 수에서 계산된다. 주인 값과 레인 수의 1:1을 설정으로 끊으면 그 순간 두 존의 틱이 한 스레드로 합쳐진다. 자세한 건 설정 파일 설계.

존 배치 — 2×2 격자

  x:0        10        20
y:20 ┌─────────┬─────────┐
     │  존 1   │  존 2   │   ← ZoneServer.exe 1,2  (프로세스 #1)
y:10 ├─────────┼─────────┤
     │  존 3   │  존 4   │   ← ZoneServer.exe 3,4  (프로세스 #2)
y: 0 └─────────┴─────────┘
zoneId는 1부터다. 0은 "존 없음/미배정" 예약값 — 0을 유효 존으로 쓰면 "0번 존에 있다"와 "아직 아무 존에도 없다"가 같은 값이 되어 구분할 수 없다.

배치를 정하는 코드는 ParseZoneList 하나뿐이고, 그 아래 계층은 담당 사각형(Def)을 그대로 들고 다녀서 격자라는 것조차 모른다.

주의 — 클라이언트의 ZoneLayout.cs와 StressClient가 같은 값을 복제한다. 한쪽만 고치면 화면 경계와 실제 핸드오프 지점이 어긋난다.

핵심 타입

타입역할보호
Zone존 하나의 게임 세계. 네 처리기가 이걸 같이 본다—
UnitContainer그 존의 유닛 전부(units_/players_)shared_mutex — BASIC이 바꾸는 동안 TICK이 돈다
└ 틱이 도는 목록유닛 포인터 배열 스냅샷없음 — TICK 전용. 그래서 병렬로 나눌 수 있다
Unit / Player자리와 틱을 갖는 공통 + 주인과 콘텐츠 모델모델마다 다름 (아래)
MoveModel위치 + 아직 반영 안 된 이동 요청Mutexed — BASIC이 쓰고 TICK이 읽는다
MailModel우편함Mutexed — BASIC(요청)과 TICK(만료 삭제)이 만난다
CurrencyModel지갑없음 — BASIC 레인 전용
ZoneUnitOfWork변경분을 모았다가 소멸자에서 결말을 낸다—

모델마다 보호가 다른 기준

"실제로 몇 개의 레인이 건드리는가" 하나다. 하나면 락이 없고, 둘이면 Mutexed다. 전부 락을 걸면 안전하지만 그건 이 프로젝트가 보여주려는 것이 아니고, 전부 안 걸면 깨진다. 자세한 건 설계 근거 문서.

UnitOfWork — 커밋 호출이 없다

상태를 바꾸는 요청은 전부 같은 모양이다: 
// ① 핸들러가 받는 packet 은 이미 파싱이 끝나 있다 (디스패치 앞에서)
UnitOfWork unitOfWork(...);            // ② 열기가 곧 트랜잭션 시작
if (실패) { unitOfWork.SetError(...); return; }  // ③ 에러만 심고 그냥 return
model.Change(..., unitOfWork);          // ④ 바뀐 내용은 Task로 기록된다
                                       // ⑤ 스코프를 벗어나는 순간 소멸자가 결말을 낸다
성공이면 한 번만 직렬화해서 World(DB)와 클라이언트로 같은 바이트를 보내고, 실패면 Task 목록을 역순으로 훑어 각자의 역연산으로 되돌린다. 호출부에 롤백 코드도, 성공/실패 분기도 없다.

되돌리는 장면: C2ZMailBuy 롤백 시퀀스
