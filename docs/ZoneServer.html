ZoneServer 게임 로직

플레이어와 존의 권위 상태를 들고 있는 서버. 이 프로젝트의 핵심이 전부 여기 있다.

한 줄 요약

프로세스 하나가 존 여러 개를 호스팅한다(ZoneServer.exe 1,2). World로 나가서 붙고(accept하지 않는다), 받은 패킷을 주인에 따라 다른 레인으로 보낸다.

레인 네 개 — 주인이 다르기 때문에 나뉜다

I/O 스레드 2개
      ↓  바이트만 복사
LB 그룹 (4)          패킷 파싱, 주인 판정. 게임 상태를 안 만진다
      ↓
Player 그룹 (8)      owner = clientSessionId   우편·재화·UnitOfWork
ZoneSpace 그룹 (존 수) owner = zoneId           로스터·좌표·경계·틱
Broadcast 그룹 (1)   owner = zoneId           팬아웃 전송
Player와 ZoneSpace를 나눈 것이 이 서버의 설계 핵심이다. "그 사람만의 것"(우편함, 지갑)과 "존 전체가 공유하는 것"(누가 이 존에 있는가, 좌표)은 주인이 다르다. 한 레인에 두면 주인을 하나로 정할 수 없어 결국 존 키로 통일되고, 그러면 그 존의 모든 콘텐츠가 스레드 하나로 직렬화된다.

실제로 겪은 일

1만 세션 부하 테스트에서 처리량이 1/39로 무너졌던 원인이 정확히 그것이었다. 콘텐츠 처리의 주인을 clientSessionId로 바꾸면서 같은 존에 사람이 몰려도 Player 레인 8개로 갈라지게 됐다.

이 수치는 설정 파일에서 온다

스레드 수·포트·주기는 config/zone.cfg에서 읽는다. 값이 틀리면 기본값으로 넘어가지 않고 기동을 멈추고, 아무도 읽지 않은 키는 경고로 남는다(오타를 잡는 유일한 수단). 자세한 건 설정 파일 설계.

존 배치 — 2×2 격자

  x:0        10        20
y:20 ┌─────────┬─────────┐
     │  존 1   │  존 2   │   ← ZoneServer.exe 1,2  (프로세스 #1)
y:10 ├─────────┼─────────┤
     │  존 3   │  존 4   │   ← ZoneServer.exe 3,4  (프로세스 #2)
y: 0 └─────────┴─────────┘
zoneId는 1부터다. 0은 "존 없음/미배정" 예약값 — 0을 유효 존으로 쓰면 "0번 존에 있다"와 "아직 아무 존에도 없다"가 같은 값이 되어 구분할 수 없다.

배치를 정하는 코드는 ParseZoneList 하나뿐이고, 그 아래 계층은 담당 사각형(Def)을 그대로 들고 다녀서 격자라는 것조차 모른다.

주의 — 클라이언트의 ZoneLayout.cs와 StressClient가 같은 값을 복제한다. 한쪽만 고치면 화면 경계와 실제 핸드오프 지점이 어긋난다.

핵심 타입

타입역할보호
Player플레이어 한 명 + 그 사람의 모델들모델마다 다름 (아래)
PlayerRegistryclientSessionId → Player없음 — 레인 수만큼 샤딩
Instance존 하나의 권위 상태(로스터·경계·틱)없음 — ZoneSpace 레인 전용
Model우편함Mutexed — 만료 스윕과 만난다
Model지갑. 값 변경 통로가 SetTracked 하나없음 — Player 레인 전용
UnitOfWork변경분을 모았다가 소멸자에서 결말을 낸다—

모델마다 보호가 다른 기준

"실제로 몇 개의 레인이 건드리는가" 하나다. 하나면 락이 없고, 둘이면 Mutexed다. 전부 락을 걸면 안전하지만 그건 이 프로젝트가 보여주려는 것이 아니고, 전부 안 걸면 깨진다. 자세한 건 설계 근거 문서.

UnitOfWork — 커밋 호출이 없다

상태를 바꾸는 요청은 전부 같은 모양이다: 
UnitOfWork uow(...);           // ① 먼저 연다 (파싱 실패도 같은 경로로 응답해야 하므로)
if (실패) { uow.SetError(...); return; }   // ② 에러만 심고 그냥 return
model.Change(..., uow);            // ③ 바뀐 내용은 Task로 기록된다
                                   // ④ 스코프를 벗어나는 순간 소멸자가 결말을 낸다
성공이면 한 번만 직렬화해서 World(DB)와 클라이언트로 같은 바이트를 보내고, 실패면 Task 목록을 역순으로 훑어 각자의 역연산으로 되돌린다. 호출부에 롤백 코드도, 성공/실패 분기도 없다.

되돌리는 장면: C2ZMailBuy 롤백 시퀀스

관련 문서

C2ZMailAdd → DBLB → Player 레인 → UoW 전 구간 존 핸드오프ZoneSpace 레인의 틱이 경계를 판정한다 Group 설계레인 어피니티의 근거와 함정
