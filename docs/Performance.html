성능 측정

자동화 스위트가 없는 대신 부하 도구를 직접 만들어 정확성 · 처리량 · 지연을 동시에 측정했다. 숫자보다 어떻게 쟀는가가 중요하다.

측정 방식

항목내용
지연 기준C2ZMailAdd 송신 → Z2CTaskResult 수신까지의 클라이언트 체감 왕복. 서버 내부 처리 시간만 재면 큐에서 밀린 시간이 빠져 실제보다 낙관적인 값이 나온다
히스토그램원시 샘플을 들고 있지 않고 551개 로그스케일 버킷에 relaxed atomic으로 기록. 수백만 샘플에도 상수 메모리·O(1)이라 측정이 실험을 방해하지 않는다
추적 상한100초. 처음엔 10초였는데 과부하 실험에서 P95·P99가 전부 최상위 버킷에 몰려 얼마나 나쁜지를 구분할 수 없었다(실제 최대는 131초). 상한에 걸린 값은 ≥100초로 구분 표기
1 사이클MailAdd → Ack → MailDel → Ack — 왕복 2회

정확성을 같이 재는 이유

"빨랐다"만으로는 락 없는 설계를 증명하지 못한다. 이 도구는 Del로 돌아온 mailId가 내가 Add해서 받은 그 mailId인가를 매 사이클 대조한다 — 스레드가 섞이면 여기서 불일치가 잡힌다.

깨진 게 아니라 느려진 것

14만 사이클(= Mail 왕복 28만 회)에서 mailId 불일치 0건, 데드락 0건, 서버 WARN/ERROR 0건, 종료 시 정상 정리. 정확성은 완전히 유지됐다. 대신 처리량이 1/39로 무너졌고 전 세션이 스톨 판정(20초 무응답)을 받았다.
원인은 "존 하나에 1만 명"이었다. 콘텐츠 처리의 주인이 zoneId였기 때문에 그 존의 모든 우편 작업이 스레드 하나로 직렬화됐고, 거기에 브로드캐스터 50명이 인구수만큼(최대 1만) 개별 프레임을 쏘는 팬아웃이 겹쳤다.

구조로 고쳤다 — 콘텐츠의 주인을 clientSessionId로 바꿔 Player 레인(8개)과 ZoneSpace 레인(존 수)을 분리했다. 같은 존에 사람이 몰려도 우편·재화 처리는 8개 레인으로 갈라진다.

다만 위 표는 그 수정 이전 숫자다

레인 분리 후 같은 시나리오를 아직 다시 돌리지 않았다. 재측정 전까지 471 사이클/초는 "고치기 전의 기록"으로만 읽어야 한다.

남은 병목 후보

#내용상태
1입장 존이 항상 하나 — FindEntryPoint()가 zoneId가 가장 작은 존만 돌려준다. 존이 4개 떠 있어도 부하 테스트 인구가 전부 존 1에 남는다미수정
2World가 라우팅과 브로드캐스트 릴레이를 같은 그룹에서 처리 — 릴레이 큐 분리 후보미수정
3브로드캐스트가 대상 1명당 프레임 1개 — 다중 대상 배칭 후보미수정

수정 계획: docs/load-test-fix-plan.md

대량 쿠폰 발급 (운영툴)

100만 장, 청크 1만 건 × 100회. 세 번 모두 메모리 중복 재시도 0건, DB 100만 건 전부 고유.

조건소요처리량
Release, World 전송 포함11.5 초87,123 장/초
Release, World 전송 제외10.5 초95,066 장/초

이 표의 핵심은 Debug↔Release 차이가 15%도 안 된다는 것

병목이 코드 생성 속도가 아니라 I/O(SqlBulkCopy 적재 + 스풀 fsync)라는 뜻이다. 더 줄이려면 CSPRNG를 최적화할 게 아니라 청크 크기나 인서트 방식을 손봐야 한다.

마지막 측정은 WorldServer를 일부러 죽인 채 돌렸는데 정상 완료됐다 — 쿠폰의 권위 저장소는 운영툴 SQL Server이고 World 전송은 부가 경로라는 설계가 의도대로 동작한 것이다.

UniqueId 실측

500만 개(5프로세스 × 10스레드): 중복 0건, 노드 배정 정확, DB 레인 분배 12.49~12.51%(이상값 12.5%).

클러스터 인덱스 관점에서는 "시간순 키라 append-only"가 발급자가 하나일 때만 성립했다 — 단일 노드는 단편화 0.428% / 페이지 채움 99.94%지만, 5개 노드가 동시에 발급하면 단편화가 98%대로 오른다. 그래도 무작위 키 대조군보다 페이지 수가 22% 적다.
