GatewayServer 접속 종단

클라이언트가 아는 유일한 서버. 게임 로직이 한 줄도 없다.

한 줄 요약

클라이언트 소켓을 받아(9000) World로 나가는 연결(9100) 하나에 순수 릴레이한다. 패킷 내용을 해석하지 않고, 앞에 clientSessionId만 붙여 넘긴다.

왜 따로 두는가

목적내용
내부 구조 은닉클라이언트는 World도 Zone도 주소를 모른다. 존이 몇 개인지, 프로세스가 몇 개인지도 모른다
접속 폭주 흡수accept·TLS·타임아웃 같은 연결 계층 부담이 게임 로직 서버까지 가지 않는다
존 이동이 투명해진다핸드오프는 World의 라우팅 테이블에서만 일어나므로 Gateway는 이동 자체를 모른다

스레드 구조

I/O 스레드 2개뿐이다. 별도 로직 큐가 없다 — 하는 일이 바이트 복사와 전달뿐이라 큐를 하나 더 두면 지연만 늘어난다. 
IoContextPool(2)
 ├ Listener(9000)   ClientLinkHandler   클라이언트 accept
 └ Connector(9100)  WorldLinkHandler    World로 나가는 연결(끊기면 재시도)

이 수치는 설정 파일에서 온다

스레드 수·포트·주기는 config/gateway.cfg에서 읽는다. 값이 틀리면 기본값으로 넘어가지 않고 기동을 멈추고, 아무도 읽지 않은 키는 경고로 남는다(오타를 잡는 유일한 수단). 자세한 건 설정 파일 설계.

패킷

방향패킷내용
G → WG2WClientConnected새 클라이언트가 붙었다. World가 존을 배정한다
G → WG2WRelay클라 패킷을 봉투에 담아 전달
G → WG2WClientDisconnected끊겼다. World가 라우팅 테이블에서 지운다
W → GW2GRelay봉투에서 꺼내 해당 클라이언트 소켓으로

봉투(ClientEnvelopeHeader)가 하는 일

Zone은 클라이언트와 직접 연결되지 않는다. 그래서 "누구에게 보내는 것인가"를 clientSessionId로 적어 World까지 들려 보내고, Gateway가 그걸 보고 실제 소켓을 고른다. 덕분에 Zone은 소켓을 하나도 모른다.

관련 문서

C2ZMailAdd → DBGateway가 ①~② 구간에서 하는 일 WorldServerGateway가 넘긴 패킷을 받아 라우팅하는 쪽

코드 위치

Server/GatewayServer/Src/
├ App/App       Listener + Connector 소유
├ Handler/ClientLinkHandler  클라이언트 accept, G2WRelay 생성
└ Handler/WorldLinkHandler   World 연결, W2GRelay 수신
