Client C# / MonoGame

존 격자·핸드오프·채팅·우편·쿠폰을 한 창에서 눈으로 확인하는 클라이언트. REPL로는 잘 안 보이는 것을 화면이 대신 보여주는 게 목적이다.

전제 — 서버 C++을 고치지 않는다

기존 프로토콜과 이미 있는 API만 쓴다. 클라이언트를 만들려고 서버를 고치기 시작하면 "클라이언트가 있어서 통과하는 테스트"가 되어버리기 때문이다.

그래서 별도 솔루션(Client/Client.slnx)이다 — C++ 솔루션에 섞으면 서버만 빌드할 때 NuGet 복원까지 끌려온다.

서버를 두드리는 세 도구와의 차이

도구목적보는 것
Client눈으로 확인존 경계를 넘는 순간, 다른 사람이 보이고 사라지는 것
ProtocolClient수동 REPL패킷 하나하나의 왕복, 에러 코드
StressClient부하처리량·지연 백분위·레인 편중

구조

Client/Client/Src/
├ GamePhase.cs      Login → Loading → InGame. Update/Draw가 이 값으로 통째로 갈린다
├ Protocol/     코덱(C++ BinaryWriter와 바이트 호환) + PacketId(C2Z/Z2C/C2W/W2C 대역만)
│               + ZoneLayout  ← 서버 ParseZoneList 규칙의 복제
├ Net/GameLink      TCP + 프레이밍. 수신은 큐에만 넣는다
├ Net/CouponClient  쿠폰 등록만 HTTP (GmTool.Web)
├ Model/WorldModel  게임 스레드 전용 상태 → 락이 없다
├ Model/CombatModel 유닛·화살·데미지 숫자. 좌표는 몬스터만 들고 있다(아래)
├ Text/GlyphAtlas   한글 글리프를 런타임에 GDI+로 굽는다 (.mgcb 미사용)
├ Ui/CombatArt      몸통·칼·활·화살·투구·HP바를 도형으로 그린다
└ Ui/               LoginScreen · LoadingScreen · ZoneView · ChatPanel · MailPanel
                    · CouponPanel · Hud

그림 리소스가 없다 — 전부 도형이다

콘텐츠 파이프라인(.mgcb)을 쓰지 않으므로 칼·활·투구도 선과 원으로 그린다. Ui/CombatArt.cs 한 곳에 모아 둔 이유가 그것이다 — 나중에 스프라이트 아틀라스를 받으면 그 파일의 함수 본문만 텍스처 그리기로 바뀌고, 좌표 계산·회전 각도·연출 타이밍은 그대로 남는다. 함수 이름도 아틀라스 프레임 이름과 1:1로 맞춰 뒀다.

방향별 프레임이 필요 없다: 서버에 방향 값이 없어서 몸통은 언제나 정면이고 무기만 각도대로 돈다. 그 각도도 "직전 좌표 → 새 좌표"에서 클라이언트가 만들어낸 값이다.

유닛 id와 플레이어 키가 같은 값이다

서버가 플레이어 유닛의 id를 clientSessionId를 uint32로 자른 값으로 발급한다. 그건 Z2CMoveNotify가 발신자를 싣는 방식과 정확히 같아서, "움직이는 원"(Players)과 "HP 바"(Units)를 키 하나로 잇는다 — 클라이언트에 변환표가 없다. 그래서 좌표의 권위는 이동 통지 쪽에 두고 CombatUnit의 좌표는 몬스터에만 쓴다.

단계를 나눈 이유

서버가 로그인을 통과하기 전에는 게임 패킷을 존으로 넘기지 않는다. 그러니 이동·채팅을 쏘아봐야 조용히 버려질 뿐이라, 클라이언트도 같은 경계를 갖고 있어야 "보냈는데 아무 일도 일어나지 않는다"가 안 생긴다. 
Login    ID/PW 입력. 서버가 떠 있든 아니든 이 화면부터 시작한다
         응답을 기다리는 동안 모달 스피너, 실패하면 에러 문구 + 닫기
         10초 무응답은 실패로 돌린다 — 팝업이 영원히 도는 것을 막는다
  ↓ W2CLogin errorCode == Success
Loading  존 배정(Z2CEnterZoneNotify)을 기다린다. 지금은 대개 한순간에 지나간다
         이 화면이 계속 보이면 ZoneServer가 World에 안 붙은 것이다
  ↓ 배정됨
InGame   존 뷰 · 채팅 · 우편 · 쿠폰. 여기서만 그린다

Loading 단계를 지금 거의 지나가는데도 둔 이유는, 나중에 실제로 로딩할 것이 생기는 자리이기 때문이다(캐릭터 정보, 리소스). 그때 단계를 새로 끼우려면 Update/Draw 분기를 다시 째야 한다.

계정이 없어도 들어가진다

서버가 자동 가입시키므로 시드에 없는 이름을 넣어도 된다. 실행 인자 --id= / --pw=로 로그인 칸을 미리 채울 수 있다(자동 로그인은 아니다 — 접속은 사람이 누른다). 창을 여러 개 띄워 서로 다른 계정으로 붙을 때 쓴다.

수신을 큐에만 넣는 이유

소켓 콜백은 별도 스레드에서 온다. 거기서 게임 상태를 직접 고치면 렌더 중인 데이터를 건드리게 된다. 큐에 넣고 게임 스레드가 프레임 시작에 꺼내 적용하면, WorldModel은 한 스레드만 만지므로 락이 필요 없다 — 서버의 Instance가 락이 없는 것과 정확히 같은 이유다.

ZoneLayout은 서버 규칙의 복제다

존 배치(kZoneSize / kZonesPerRow / kZoneRows)를 클라이언트가 따로 들고 있다. 한쪽만 고치면 화면에 그려지는 경계와 실제 핸드오프 지점이 어긋난다. 서버가 존 경계를 패킷으로 알려주는 것이 맞고, 그건 존 입장 스냅샷 작업과 한 세트다(아직 없음).

쿠폰만 경로가 다르다

쿠폰 등록  →  HTTP  →  GmTool.Web
보상 수령  ←  소켓  ←  우편(Z2CTaskResult)
쿠폰은 게임 패킷이 아니라 운영툴의 HTTP API로 나가고, 결과는 우편으로 돌아온다. 운영툴이 우편을 보낼 때 새 패킷을 만들지 않고 기존 C2ZMailAdd를 봉투에 감싸 주입하기 때문에, 존 입장에서는 클라이언트가 직접 보낸 것과 바이트 단위로 구분되지 않는다.

현재 한계 — 클라이언트가 메워주고 있는 것

브로드캐스트는 그 순간 존에 있는 사람에게만 간다. 입장할 때 기존 플레이어 목록을 주는 패킷도, 누가 나갔는지 알리는 패킷도 없다.

그래서 지금은 클라이언트가 좌표 하트비트(1초)와 타임아웃(6초)으로 메우고 있다. 서버가 Z2CEnterZoneNotify에 존 안의 플레이어 스냅샷을 싣고 퇴장을 브로드캐스트하는 쪽이 맞다 — AOI를 넣으면 어차피 서버가 판단해야 하므로 그 작업과 한 세트다.

프로세스를 넘으면 존에서 만든 우편이 사라진다

World가 로그인 때 읽어둔 우편·재화는 핸드오프에도 다시 실려 가므로 살아남는다. 그런데 World 캐시가 로그인 시점의 DB 스냅샷에서 멈춰 있다 — 존에서 새로 만든 우편을 World가 모르기 때문에, 프로세스를 넘는 이동(세로)에서는 그것만 사라진다. 같은 프로세스 안의 가로 이동은 Player 객체가 그대로 살아 있어 영향이 없다.

클라이언트는 이걸 감추지 않고 MailboxResetByZoneChange로 서버와 같은 상태로 맞춰 비운다 — 화면만 남겨두면 삭제를 눌렀을 때 MailNotFound만 돌아온다. 서버가 존이 올린 UnitOfWork를 캐시에 반영하면 이 처리도 같이 없어진다.

실행

bat\start_client.bat 2            :: 창 2개 (브로드캐스트 확인에는 최소 2개)
bat\start_client.bat 2 Debug auto :: 자동 순회 — 짝수 창은 반대 방향으로 돈다

첫 화면은 로그인이다. 기본값은 tester1 / 0000(시드 계정).
조작: WASD/방향키 이동, 빈 곳 클릭으로 순간 이동, 유닛 클릭 또는 Tab으로 타겟, Space 공격, 1/2 근접·원거리 전환, Enter 채팅, F1 Echo 핑, F2 자동 순회, Esc 패널 닫기.

자동 순회(F2)를 켜면 알아서 싸운다 — 가장 가까운 몬스터를 골라 계속 때린다. 사람이 안 보고 있어도 공격 → 데미지 → 사망 → 리스폰 → 몬스터 반격이 계속 도는지 확인하려는 것이다.
