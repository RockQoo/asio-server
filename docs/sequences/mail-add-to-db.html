이 그림에서 봐야 할 것

① 클라이언트 응답과 DB 저장은 같은 바이트에서 갈라진다

⑥에서 한 번만 직렬화한 Task 스트림이 ⑦(World→DB)과 ⑧(클라이언트)로 똑같이 나간다. 두 경로가 따로 만들어지면 "클라 화면엔 있는데 DB엔 없는 우편"이 생긴다 — 그걸 구조적으로 막은 것이다.

② 스레드가 네 번 바뀌는데 락은 한 군데뿐이다

Gateway I/O → World Main → Zone LB → Zone Player → World DB. 이 중 락을 쓰는 곳은 ⑤의 우편함(Mutexed)뿐이고, 그것도 만료 스윕 타이머와 만나기 때문이다. 나머지는 전부 "같은 주인의 일은 같은 스레드"(ownerId % N)로 해결한다.

③ 실패해도 경로가 같다

우편함 없음이든 잔액 부족이든, UoW에 에러만 설정하고 스코프를 벗어난다. 소멸자가 역순 롤백 후 ⑧과 같은 Z2CTaskResult로 에러 코드를 보낸다 — 호출부에 성공/실패 분기가 없다. 되돌리는 장면은 C2ZMailBuy 롤백에서 볼 수 있다.

④ 주인이 두 번 바뀐다

Zone에서는 clientSessionId가 주인이고, World의 BASIC 레인까지도 같다 — 그래야 그 사람의 라우팅·캐시·접속 종료가 한 줄로 처리된다. DB 레인에 들어갈 때만 playerId로 갈아탄다: DB 작업은 세션이 아니라 계정에 묶이는 일이라, 재접속해서 세션 번호가 바뀌어도 한 계정의 쓰기는 같은 레인에서 도착 순서대로 직렬화돼야 한다. 갈아탈 때 쓰는 playerId는 존이 실어 보낸 값이 아니라 로그인이 확정해 캐시에 넣어둔 값이다.
