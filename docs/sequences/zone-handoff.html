존 핸드오프 — 재접속 없이 존을 넘어간다

존 경계를 넘는 C2ZMove. World는 라우팅 테이블만 바꾼다 — Gateway는 이동이 일어난 줄도 모르고, 클라이언트는 같은 TCP 연결을 그대로 쓴다.

가로 이동과 세로 이동이 다르다

존은 2×2 격자(1 2 / 3 4)이고 기본 기동은 프로세스 2개다 — 위쪽 행(존 1,2)과 아래쪽 행(존 3,4)을 나눠 담당한다.
이동경로비용
가로 (1 ↔ 2, 3 ↔ 4)같은 프로세스의 스레드 간큐 하나 건너뛰기
세로 (1 ↔ 3, 2 ↔ 4)프로세스 간 — World를 거쳐 TCP 링크로직렬화 + 소켓 왕복
위 그림은 세로(존 1 → 존 3) 경우다. 가로는 ⑨가 다르다: World가 대상에 W2ZEnterZone만 보내고 퇴장은 보내지 않는다 — 같은 프로세스라 PlayerProcessor가 살아 있는 Player를 그대로 옮기면 되고, 퇴장을 보내면 우편함째 지워버린다. 나머지 단계는 같다 — 존 입장에서 "어느 프로세스에 있는가"는 알 필요가 없다.

왜 이렇게 두었나

한 화면에서 두 경로를 비교하려는 것이다. 분산 서버에서 진짜 비용이 드는 건 프로세스 경계인데, 같은 기능이 어떤 때는 스레드 간이고 어떤 때는 프로세스 간이라는 걸 보여주려면 둘 다 실제로 일어나야 한다.

프로세스를 넘을 때 우편함은 World 캐시를 타고 간다

객체를 프로세스 사이로 옮길 수 없으니, 전입한 존은 W2ZEnterZone에 실려 온 World 캐시의 우편·재화로 모델을 다시 만든다. 그 캐시는 로그인 때 DB에서 채우고, 이후 존이 올린 Z2WUnitOfWorkStream을 BASIC 레인에서 계속 반영해 최신으로 유지한다 — 스트림과 핸드오프 요청이 같은 TCP 링크로 오고 같은 주인(clientSessionId)의 같은 strand에서 처리되므로, 직전에 만든 우편도 이미 캐시에 들어 있다.

그래서 원본 프로세스에 퇴장을 보내야 한다. 안 보내면 그쪽에 Player와 우편함이 유령으로 남아, 만료 스윕이 같은 우편을 한 번 더 지우고 클라이언트도 삭제 통지를 두 번 받는다(실제로 겪었다 — 삭제 태스크의 RUID 노드 번호가 서로 다른 두 프로세스를 가리켰다). 접속이 끝날 때까지 안 지워지므로 메모리도 샌다. 판정 기준은 zoneId가 아니라 링크 세션이다 — 한 Zone 프로세스가 존 여러 개를 맡는다.

그리고 — 입장 존이 항상 하나다

FindEntryPoint()가 zoneId가 가장 작은 존의 중앙만 돌려줘서, 존이 4개 떠 있어도 신규 접속이 전부 존 1로 간다. 눈으로 보는 클라이언트는 곧 흩어지므로 문제가 안 되지만, 부하 테스트에서는 1만 명이 한 존에 남는다.
