C2ZMailBuy — 모델 두 개에 걸친 트랜잭션과 역순 롤백

우편 지급 + 골드 차감을 한 UnitOfWork로 묶는다. 골드가 모자라면 이미 들어간 우편을 되돌려야 하는데 — 그 되돌리는 장면이 이 프로젝트에서 실제로 밟히는 유일한 경로다.

Client Gateway / World 릴레이 Zone Player 레인 모델 (MailModel / CurrencyModel)
Client게임 스레드
Gateway → World순수 릴레이 + 라우팅
PlayerProcessorPlayer 레인
MailModel우편함 (Mutexed)
CurrencyModel지갑 (값)
ZoneUnitOfWorkTask 목록
① C2ZMailBuy title / body / durationSec / price
② G2WRelay → W2ZRelay Gateway는 내용을 모르고, World는 zoneId만 보고 넘긴다
③ UnitOfWork를 먼저 연다 requestId를 UniqueIdGenerator로 발급한다 — 이 요청 하나를 전 서버에서 같은 값으로 가리키기 위해서.
④ AddMail(info, uow) 우편이 먼저다 — 순서가 뒤집히면 되돌릴 것이 없어진다
⑤ AddMailTask 기록 우편함 메모리는 이미 바뀌었고, 되돌리는 법은 Task가 안다
⑥ DecCurrency(Gold, price, uow)
⑦ 잔액 부족 값을 바꾸는 통로가 SetTracked 하나라서 검증·이전값 포착·Task 기록이 전부 여기 한 자리에서 일어난다. Task를 남기지 않고 실패를 반환
⑧ EErrorCode::NotEnoughCurrency [[nodiscard]]라 호출부가 무시할 수 없다
⑨ unitOfWork.SetError(...) 그리고 그냥 return한다. 여기에 롤백 코드가 없다는 것이 요점이다.
⑩ 소멸자 — HasError() RollbackAll()이 Task 목록을 역순으로 훑는다. 무엇을 되돌릴지 고르는 switch가 없다 — 각 Task가 자기 역연산을 안다.
⑪ AddMailTask::Rollback() ④에서 넣은 우편을 우편함에서 도로 뺀다
⑫ Z2CTaskResult (errorCode, 빈 스트림) 되돌렸으므로 클라이언트가 적용할 Task가 없다 — 에러 코드만 간다

성공했다면 — 여기가 테스트 6·7번이다

⑦에서 잔액이 충분했다면 DecCurrencyTask가 하나 더 쌓이고, 소멸자는 롤백 대신 Task 2개를 한 번에 내보낸다: 
Z2WUnitOfWorkStream  →  World DB 레인  →  AutoDbCommand(ownerId, useTransaction = true)
                                              ├ up_mails_upsert       (@is_trans_outside = 1)
                                              ├ up_currencies_upsert  (@is_trans_outside = 1)
                                              └ COMMIT   /  예외면 ROLLBACK
UnitOfWork 하나 = AutoDbCommand 하나 = 트랜잭션 하나. 여러 UoW를 모으지 않는다. @is_trans_outside는 "바깥이 이미 트랜잭션을 열었다"를 SP에 알리는 파라미터다 — 모르면 SP가 자기 트랜잭션을 또 열어 중첩이 되고, 그러면 안쪽 COMMIT이 실제로 커밋하지 않는다.

지금 상태

메모리 쪽(①~⑫)은 전부 동작하고 롤백도 실측했다. DB 쪽은 배선만 남았다 — ZoneLinkHandler가 Task를 훑기만 하고 AutoDbCommand를 만들지 않는다. 자세한 건 C2ZMailAdd 경로의 ⑫ 참고.

왜 우편을 먼저 넣는가

골드를 먼저 깎으면 실패 시점에 되돌릴 것이 없다 — 그러면 롤백 코드가 한 번도 실행되지 않고, "되돌릴 수 있다"가 주장으로만 남는다. 순서를 이렇게 둔 덕에 이 경로가 역순 롤백의 실측 대상이 된다. 실무에서도 같은 이유로 "되돌리기 어려운 것을 나중에" 둔다.
