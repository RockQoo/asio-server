성능 점검표

2026-09-18 측정 · 존을 다섯 레인 구조로 바꾼 직후의 기준선이다. 개선 전 수치이고, 개선 후 같은 표를 다시 채운다.

이 숫자를 절대 성능으로 읽지 말 것 — Debug 빌드다.

Release 로 재면 자릿수가 달라진다. 여기 있는 값은 구간끼리 비교하고 개선 전후를 비교하기 위한 것이다. "초당 몇 건이 나오는 서버인가"에 대한 답이 아니다.

1. 무엇을 보고 판단했나

처리량 숫자 하나로는 서버의 좋고 나쁨을 못 가른다. 장비가 바뀌면 그대로 바뀌는 값이기 때문이다. 그래서 장비가 달라도 성립하는 성질만 골라 점검표로 만들었다.

통과 실패 결함 확인됨 미측정
#기준판정근거
1 접속자 1명당 비용이 인원에 따라 늘지 않는가
가장 결정적인 항목. 여기가 깨지면 장비를 늘려도 못 막는다		 실패 이동 통지가 그 존 전원에게 나간다. 1명당 팬아웃이 100명일 때 99통, 1500명일 때 1,499통 — 인원 15배에 1인당 비용도 15배라 총량이 225배가 된다
2 스레드를 늘리면 처리량이 따라 오르는가 미측정 1번을 고치기 전에는 재도 의미가 없다. 팬아웃이 먼저 막혀서 스레드가 놀지 않는다
3 포화했을 때 원인을 지목할 수 있는가 통과 중계 서버의 레인 적체 5,511,733 건으로 지점이 특정됐고, 원인도 특정됐다(3절)
4 어디가 밀렸는지 보이는가 통과 레인별 적체와 송신 적체가 주기적으로 로그에 남는다. 이게 없었으면 3번을 못 했다
5 p99 지연이 p50 에 가까운가 미측정 평균만 재고 있다. "평균 33ms"는 절반이 500ms 여도 나오는 숫자라 사실상 품질을 못 보고 있는 상태다
6 받아들인 요청을 잃지 않는가 통과 DB 회차 5만 건 유실 0 · 불일치 0. 100명 이동 회차 10분간 도달률 1.0
7 무너지는 방식이 얌전한가 실패 크래시도 데이터 손상도 없었지만 큐에 상한이 없다. 메모리가 11MB → 5,211MB 로 늘었고 부하를 뺀 뒤에도 안 줄었다

3. 병목 — 존이 아니라 중계다

존 CPU 290초 / 중계 서버 CPU 2,294초로 8배 차이가 났다.

존     : 팬아웃 수백 통을 한 덩어리로 묶어 한 번에 쓴다
           |
중계   : 봉투를 한 통씩 까서 한 통씩 다시 씌운다      <-- 여기서 묶음이 풀린다
           |
게이트웨이: 클라이언트로 전달

존에서 묶은 이득이 중계에서 통째로 사라진다. 이건 통지 양을 줄여도 남는 문제다 — 중계 구간이 여전히 건건이 포장을 다시 하기 때문이다.

4. 목표선

존 하나에 1,500명을 목표로 잡았다. 그 인원이 요구하는 양을 역산하면:

시야 안의 사람에게만 보낼 때   1,500명 x 초당 5회 x 주변 50명 =   375,000 통/초
존 전원에게 보낼 때(현재)      1,500명 x 초당 5회 x 1,499명    = 11,240,000 통/초

초당 5회는 가정값이다. 실제 클라이언트 전송 빈도를 정하면 이 표를 다시 계산한다.
