WorldServer 라우팅 + DB

누가 어느 존에 있는지 아는 유일한 서버. 그리고 DB로 나가는 유일한 관문.

한 줄 요약

포트 셋을 열어(Gateway 9100 / Zone 9200 / 운영툴 9300) 로그인을 처리하고, 클라이언트 패킷을 담당 존으로, 존이 올린 변경분을 DB로 보낸다. 존 이동은 여기 라우팅 테이블 한 줄로 끝난다.

스레드 구조 — 그룹 두 개

I/O 스레드 2개        소켓에서 바이트만 복사, ownerId를 훔쳐보고 큐에 넣는다
      ↓
Basic 그룹 (스레드 8 + strand 8)
      ├ Main 프로세서   클라이언트 라우팅 (PlayerManager / ZoneLinkRegistry)
      ├ Login 프로세서  로그인 결과 반영 + 존 입장
      ├ Tool 프로세서   운영툴 명령
      └ Test 프로세서   F키 테스트 메시지(PushMsg → Message::Router)
      ↓
Db 그룹 (스레드 4 + strand 4)     블로킹을 허용하는 별도 그룹. owner = playerId
      └ Db 프로세서     UnitOfWork 적재 · 로그인 계정 조회/생성/콘텐츠 적재
세 프로세서가 한 그룹을 공유한다. 프로세서는 스레드가 아니라 "그 스레드 위에서 어느 함수를 부르는가"를 가르는 태그다 — 어느 스레드에서 도는지는 메시지의 주인이 정한다.

Zone과 여기가 다르다

Zone은 모든 메시지가 주인을 갖는다(playerId / 존 서수 / zoneId). 그래서 어느 데이터든 한 번에 한 스레드만 만지고, 모델에 락이 거의 없다.

World도 같다. 다만 하는 일이 대부분 릴레이라 주인이 그 사람(로그인 전 세션 id, 이후 playerId)인 경우가 대부분이고, 전체 대상이라 사람이 주인이 아닌 것만 고정 상수를 쓴다:

PushMsg<Basic>(msgType, 프로세서id, ownerId, body)

  ownerId 가 레인을 정한다. 같은 주인끼리는 겹치지 않고 보낸 순서대로.
  그래서 그 주인으로 갈리는 상태에는 락이 없다.

  주인이 없는 일(전체 공지)도 고정 상수 하나를 줘서 한 레인에 직렬화한다 --
  주인을 안 주는 경로는 만들지 않는다.

그래서 World의 전역 테이블(PlayerManager / ZoneLinkRegistry)은 Thread::Mutexed다. 지금 주인 없이 도는 것은 전체 공지 하나뿐이고, 나머지는 전부 순서가 필요하다.

"같은 스레드"가 아니라 "직렬화"다

레인을 굴리는 방식이 둘인데(config 로 고른다), strand 쪽은 겹치지 않음 · 보낸 순서 · 앞 작업의 쓰기가 뒤에 보임을 보장하지만 매번 같은 스레드를 쓰지는 않는다. 락 없는 접근에 필요한 조건은 그 셋이고 스레드 정체성은 아니다.

대가는 하나 — thread_local에 기대면 안 된다. DB 커넥션이 스레드당 하나인 것은 그대로 유효하지만(커넥션 수 = 스레드 수), 커넥션에 세션 상태를 남기고 다음 작업이 그걸 기대하면 깨진다.

로그인 — 레인을 네 번 갈아탄다

Basic(Login, owner=clientSessionId)    C2WLogin 파싱 / 중복 로그인 거절
      ↓
Db(Db, owner=clientSessionId)          usp_players_select → 비밀번호 검증
                                       없으면 RUID 발급 + usp_players_upsert (자동 가입)
      ↓
Db(Db, owner=clientSessionId)          usp_players_load → 우편 · 재화
      ↓
Basic(Login, owner=clientSessionId)    캐시 적재 → W2CLogin → W2ZEnterZone(콘텐츠 동봉)
계정이 없는 것은 실패가 아니다 — 그 자리에서 만들고 성공으로 돌려준다. 그래서 에러 코드에 "없는 계정"이 없고, 있어서도 안 된다.

레인은 갈아타도 주인은 안 바뀐다. playerId를 알게 된 뒤에도 clientSessionId를 그대로 쓴다 — 중간에 갈아타면 그 지점부터 앞 구간과 직렬화가 끊겨, 같은 세션의 로그인 단계들이 서로 다른 strand에서 겹친다. 존 입장 뒤의 UnitOfWork만 playerId가 주인이다. 그건 세션이 아니라 계정에 묶이는 일이라 재접속해도 같은 레인을 유지해야 하고, 로그인은 그 세션 안에서만 의미가 있어 기준이 다르다.

적재 실패는 로그인 실패로 끊는다

빈 캐시로 들여보내면 그 사람의 우편과 재화가 없는 것으로 보이고, 그 상태에서 뭔가를 쓰면 DB의 실제 값을 덮어쓴다 — 재화는 증감이 아니라 절대값 UPDATE라 잔액이 그대로 사라진다.

World가 클라이언트 패킷을 들여다보는 유일한 자리

MainProcessor::HandleFromClient는 봉투 안 id의 방향이 C2W면 존으로 넘기지 않고 LoginProcessor로 보낸다. 대역으로 가르므로 로그인 말고 다른 C2W 패킷이 생겨도 이 분기는 그대로다.

인증 전에는 게임 패킷이 존까지 가지 않는다. TCP 연결만으로 게임이 시작되던 동작이 여기서 끝났다 — G2WClientConnected는 등록만 하고, 존 입장은 로그인 성공 시점이다.

DB 그룹을 따로 둔 이유

DB 호출은 블로킹이다. 라우팅 레인에서 같이 하면 쿼리 한 번이 그 레인에 걸린 모든 사람의 패킷을 멈춘다. 그래서 "막혀도 되는 일"만 모아 별도 그룹에 둔다.

이 수치는 설정 파일에서 온다

스레드 수·포트·주기는 config/world.cfg에서 읽는다. 값이 틀리면 기본값으로 넘어가지 않고 기동을 멈추고, 아무도 읽지 않은 키는 경고로 남는다(오타를 잡는 유일한 수단). 자세한 건 설정 파일 설계.

핵심 타입

타입역할락
PlayerManager접속 중인 플레이어 전원 — 라우팅(게이트웨이 링크, zoneId) + 계정(playerId, 인증) + 콘텐츠 캐시(우편·재화)Mutexed — 어느 스레드에서든 읽힌다
ZoneLinkRegistryzoneId → (zoneSession, 담당 사각형)Mutexed — 같은 이유
MainProcessorBASIC 레인(Main)의 라우팅 처리기. 링크 핸들러가 I/O 스레드에서 던진 일이 실제로 도는 곳없음 — 레인 규약
LoginProcessorC2W 대역 처리. 계정 조회·자동 가입·콘텐츠 적재·존 입장없음 — 레인 규약
DbProcessorDB 레인(Db)의 처리기. 커넥션 획득 + 트랜잭션 + 실패 정책(Fire-and-Forget) + 콜백없음 — 레인 규약
AutoSpCommandsSP 커맨드를 모았다가 소멸 시 DbProcessor로 한 번에. 실행·실패 정책은 그쪽—
DbConnectionODBC 커넥션 하나. 레인 스레드마다 thread_local 1개없음 — 1:1이라 공유가 없다
ToolProcessor운영툴 전용 포트(9300)의 핸들러없음 — 다른 링크와 같은 스레드 규약

존 이동 = 라우팅 테이블 한 줄

존이 "이 사람이 내 사각형을 벗어났다"고 알려오면, World가 좌표로 대상 존을 찾아 playerManager_.Write()->SetZoneId(clientSessionId, 대상) 한 줄을 실행한다. 그게 핸드오프의 전부다. 클라이언트는 재접속도 재인증도 하지 않는다.

전입하는 존에는 캐시의 우편·재화를 다시 실어 보낸다(W2ZEnterZone) — 그래야 새 존이 빈 모델로 시작하지 않는다. 그 캐시는 아래 "DB로 나가는 길"에서 계속 갱신되므로 로그인 시점 스냅샷이 아니라 지금 상태다.

프로세스를 넘는 이동이면 원본 존 링크에 W2ZLeaveZone도 보낸다. 안 보내면 그쪽 프로세스에 그 사람의 Player와 우편함이 유령으로 남아, 만료 스윕이 같은 우편을 두 번 지운다. 같은 프로세스 안의 이동에는 보내지 않는다 — 그쪽은 살아 있는 Player를 그대로 옮기므로 퇴장을 보내면 우편함째 지워진다. 판정 기준은 zoneId가 아니라 링크 세션이다.

자세한 흐름: 존 핸드오프 시퀀스

DB로 나가는 길

존이 Z2WUnitOfWorkStream을 올리면 다른 패킷과 같이 Basic 레인으로 들어간다 (owner = clientSessionId). 거기서 World 캐시를 갱신하고, DB 작업만 playerId를 주인으로 Db 그룹에 넘긴다. 
Z2WUnitOfWorkStream  →  basicGroup_.Post(Main, clientSessionId)
                          ├ PlayerManager 캐시 반영 (AddMail / RemoveMail / SetCurrency)
                          └ AutoSpCommands(playerId, useTransaction = true)
                              ├ usp_mails_upsert       (@is_trans_outside = 1)
                              ├ usp_currencies_upsert  (@is_trans_outside = 1)
                              └ COMMIT   /  예외면 ROLLBACK
UnitOfWork 하나 = AutoSpCommands 하나 = 트랜잭션 하나. 여러 UoW를 모으지 않는다.

주인이 두 번 바뀐다. Zone과 World Basic 레인까지는 clientSessionId가 주인이고, Db 레인에서만 playerId로 갈아탄다 — DB 작업은 세션이 아니라 계정에 묶이는 일이라 재접속해도 같은 레인을 유지해야 한 계정의 쓰기가 도착 순서대로 직렬화된다. 그때 쓰는 playerId는 존이 실어 보낸 값이 아니라 로그인이 확정해 캐시에 넣어둔 값이다.

아직 안 된 것

  • 위조 검증 — 존이 올린 Task를 캐시에 반영하기만 하고 대조하지는 않는다. "없는 우편을 지웠다"거나 "가진 적 없는 재화를 썼다"를 걸러낼 자리가 여기다
  • DB 실패의 결말 — 쓰기가 실패해도 되돌리지 않는다(Fire-and-Forget). 메모리를 권위로 보고 어긋난 사실만 LOG.Error로 남긴다
  • 중복 로그인 — 같은 계정으로 여러 연결이 동시에 붙는다
  • 공통 콘텐츠 — 길드처럼 여러 존에 걸친 것이 들어올 자리
