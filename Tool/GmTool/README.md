# GmTool (운영툴)

**서버 기능을 검증하기 위한 도구.** 운영툴 형태를 갖췄지만 실제 서비스 운영에 투입할 물건이
아니라, 우편·공지·쿠폰 흐름이 서버에서 제대로 도는지 확인하는 데 쓴다.
C# / .NET 10 / Blazor Web App + SQL Server.

`asio-server.slnx`와 별도 솔루션(`GmTool.slnx`)이다 — C++ 솔루션에 섞으면 서버만 빌드할 때
NuGet 복원까지 끌려온다.

> **기능 개발은 현재 중단했다.** 지금은 코드 정리·문서 정합성만 손댄다(필요해지면 다시 개발).

## 기능

| 기능 | 내용 |
|---|---|
| 로그인 | 웹은 쿠키, HTTP API는 HMAC 토큰. 비밀번호는 PBKDF2(HMAC-SHA256) |
| 우편 발송 / 삭제 | WorldServer 전용 포트(9300)로 패킷 전송 → Zone이 실제 우편을 만든다 |
| 전체 공지 | 같은 경로로 접속 중 전원에게 브로드캐스트 |
| 접속자 조회 | 지금 붙어 있는 클라이언트 목록(우편 대상 선택용) |
| 쿠폰 | 캠페인 등록 → 대량 발급 → CSV 내려받기 → 등록(사용) 및 보상 우편 지급 |
| 감사 기록 | 나간 모든 명령을 `gm_command_log`에 남긴다 |

## 실행

```
bat\start_gmtool_mssql.bat    SQL Server 컨테이너 + gmtool DB/로그인 준비
bat\start_server_all.bat      World → Zone → Gateway (우편/공지를 쓸 때만 필요)
bat\start_gmtool.bat          http://127.0.0.1:5080
```

초기 계정 **`admin` / `admin1234!`**. 운영자 계정이 하나도 없을 때만 만들어지므로, 로그인 후
바꾸면 재시작 때 되돌아가지 않는다.

기동 시 `Sql/schema.sql`이 자동 적용된다(`Database:ApplySchemaOnStartup`으로 끌 수 있다).

**의존성**: 실질적으로 필요한 건 SQL Server뿐이다. WorldServer가 없어도 웹은 뜨고 로그인·쿠폰
발급까지 되며 화면에 "World 연결 끊김"으로 표시된다(우편/공지만 못 나간다). 반대로 DB가 없으면
웹은 뜨지만 계정 조회를 못 해서 로그인이 안 된다.

## 테스트

```
dotnet test GmTool.slnx
```

xUnit 77개. 전부 `GmTool.Core`(쿠폰 코드/체크문자/배치 생성/와이어 코덱)를 보고 DB를 참조하지
않는다. 저장 계층은 실제 DB를 띄워 API로 왕복 확인한다.

```

```

# 설계 노트

코드를 읽기 전에 알아두면 좋은 결정들. 코드 주석은 이 문서에 없는 국소적인 이유만 남겼다.

## 게임 DB를 직접 건드리지 않는다

우편 발송을 SQL로 직접 INSERT하지 않고 9300 포트로 패킷을 보낸다. **접속 중인 플레이어의
권위 있는 상태는 DB가 아니라 ZoneServer의 메모리**(`ZoneWorld`, `MailModel`)에 있기 때문이다.
DB를 직접 고치면 서버가 나중에 자기 메모리를 내려쓰면서 그 변경을 덮어쓴다(lost update).

그래서 이 툴의 DB에는 운영툴 자기 데이터만 있다 — 운영자 계정, 명령 로그, 쿠폰. 게임
데이터(캐릭터·우편·인벤토리)는 한 테이블도 없다.

## Blazor Server와 Minimal API가 같이 있는 이유

웹 UI는 `@rendermode InteractiveServer`로 돌고, 스크립트가 두드리는 HTTP 엔드포인트는 Minimal
API로 따로 둔다. 인증도 그래서 두 갈래다(쿠키 / HMAC 토큰).

**로그인·로그아웃 페이지만 의도적으로 정적 SSR**이다 — 쿠키 발급은 응답 헤더를 써야 하는데
Blazor Server 회로 안에서는 헤더가 이미 나간 뒤라 쓸 수 없다.

## 쿠폰

코드는 25자리 Crockford Base32(`0123456789ABCDEFGHJKMNPQRSTVWXYZ` — `I`/`L`/`O`/`U` 없음,
손으로 옮겨 적을 때 헷갈리는 글자를 뺐다).

```
MFPTZ-00024-J47EE-GZDHV-G109A
└─┬─┘ └──────────┬───────┘└┬┘
캠페인 5자리    난수 18자리  체크 2자리
```

**캠페인 코드가 네임스페이스**라는 것이 핵심이다. 전역 유일성 검사가 필요한 대상은 이 5자리
뿐이고(1년에 수십~수백 건), 그 아래 수백만 개 쿠폰 번호는 캠페인 전용 테이블 안에서만
유일하면 된다. 그래서 캠페인마다 테이블을 하나씩 동적으로 만든다(`coupon_<소문자코드>`).
파티셔닝과 같은 효과다:

- 인덱스가 캠페인 하나 크기로 유지된다
- 코드 앞 5자리로 대상 테이블이 곧바로 정해져 라우팅에 별도 조회가 없다
- 캠페인이 끝나면 그 테이블만 `DROP`하면 된다
- 동시 발급이 서로 다른 테이블로 가서 잠금 경합이 없다

대가: "전체 쿠폰"을 한 번에 조회하는 질의가 불가능해지고(캠페인 수만큼 `UNION`), 테이블 개수가
캠페인 수만큼 늘어난다. 쿠폰 접근은 거의 항상 코드 하나 또는 캠페인 하나 단위라 남는 장사다.

체크 2자리는 **DB를 조회하기 전에** 형식만으로 오타·무작위 대입을 걸러낸다. 등록 실패는 이유를
구분해 `coupon_redeem_attempt`에 남기지만 **응답은 항상 "유효하지 않은 쿠폰입니다" 한 가지다**
— 어느 코드가 존재하는지를 응답으로 알려주지 않기 위한 것이고, IP 기준 레이트 리밋(실패 10회 후
지수 백오프 5→10→20→40→80초)이 함께 걸린다.

대량 발급은 **메모리에서 생성 → 스풀 파일에 먼저 기록(fsync) → 청크 단위 벌크 적재** 순서다.
스풀 파일과 `inserted_count`가 중간에 죽었을 때의 재개 지점이 된다. World로는
`CouponChunkPush`로 200장씩 밀어주는데, **World가 죽어 있어도 발급은 정상 완료된다**(부가 경로).

### 실측 (100만 장, 청크 1만 × 100회)

| 조건 | 소요 | 처리량 | 중복 재시도 |
|---|---|---|---|
| Release | 11.3초 | **88,464 장/초** | 0 |
| Debug | 11.9초 | 83,977 장/초 | 0 |

Debug↔Release 차이가 5% 미만이라는 게 요점이다 — 병목이 코드 생성이 아니라 **I/O**(벌크 적재 +
스풀 fsync)라는 뜻이다. CSV 100만 행 내려받기는 약 0.6초(30MB, 스트리밍).

## SQL Server를 쓰는 이유

원래 MySQL로 만들었다가 옮겼다. 결정적인 건 C++ 서버 쪽 사정이다 — 나중에 `WorldServer`의
`Db::DbWorker`가 실제 DB를 붙일 때 SQL Server는 **ODBC(`<sql.h>` + `odbc32.lib`)가 Windows SDK
내장**이라 `3rd/`에 바이너리 의존성이 하나도 늘지 않는다. MySQL은 `libmysql`이나 MariaDB
Connector/C를 벤더링해야 한다. `3rd/`에는 asio 하나만 있고 "clone하면 VS 2022로 바로 빌드"가
이 저장소의 방침이라 이 차이가 컸다.

부수 이득으로 대량 적재에 `SqlBulkCopy`를 쓸 수 있고, 나중에 게임 데이터를 이 툴에서도
조회하게 되면 공유 쿼리를 저장 프로시저 한 군데로 모아 C++와 C#이 같은 SP를 호출할 수 있다.

### 이관하면서 걸린 것들

같은 함정을 다시 밟지 않기 위한 기록이다.

- **`Microsoft.Data.SqlClient`는 `ushort`/`uint`/`ulong`을 파라미터로 거부한다.** T-SQL에 부호
  없는 정수 타입이 없어서다(`byte`/`short`/`int`/`long`만 허용). 모델은 와이어 프로토콜과
  맞추려고 부호 없는 타입을 유지하고, 변환은 저장 계층 경계에서만 한다(`Data/SqlNum.cs`).
- **파라미터는 한 명령에 2,100개가 상한**이라 1만 행짜리 `INSERT ... VALUES (@c0),(@c1)...`이
  애초에 불가능하다. `SqlBulkCopy`로 세션 임시 테이블에 넣고 집합 연산으로 옮긴다.
- **`INSERT IGNORE`가 없다.** `IGNORE_DUP_KEY` 옵션은 중복을 조용히 버리지만 `@@ROWCOUNT`가
  시도 건수를 돌려줘서 실제 적재 수를 알 수 없다. 재개 지점 판단에 그 숫자를 쓰므로
  `WHERE NOT EXISTS`를 택했다.
- **`GO`는 T-SQL 문법이 아니다.** sqlcmd/SSMS의 배치 구분자라 `SqlClient`에 그대로 넘기면 문법
  오류가 난다. `DatabaseInitializer`가 줄 단위로 쪼개서 실행한다.
- **한글 컬럼은 `NVARCHAR`여야 한다.** `VARCHAR`는 DB 콜레이션의 코드페이지를 따르므로 컨테이너
  기본 콜레이션에서 `?`로 깨진다.
- `coupon_code`에 `CHAR` 파라미터를 명시하는 이유: `NVARCHAR`로 넘기면 계획에
  `GetRangeThroughConvert`가 붙는다. 지금 콜레이션(`Latin1_General_BIN2`)에서는 탐색이
  유지되므로 성능 붕괴는 아니지만(100만 행에서 논리적 읽기 3, 양쪽 동일), 불필요한 변환을
  계획에 남길 이유가 없다. 레거시 `SQL_*` 콜레이션이면 그때는 실제로 스캔이 된다.

## 알아둘 동작 (버그 아님)

**웹 UI에 로그인하면 그 계정의 API 토큰이 회수된다.** 중복 로그인 차단이 의도대로 도는
것이다(살아있는 토큰을 DB에 두고 새 로그인 시 이전 것을 revoke). UI와 스크립트를 같이 쓰려면
계정을 나눠야 한다.

## 지금 범위 밖으로 둔 것

검증 도구라는 목적에 필요하지 않아 **의도적으로 넣지 않은** 것들이다. 미완성이 아니라 선택이다.

- **역할(role) 검사.** `gm_operator.role`에 `Admin`/`Operator`가 있고 로그인 시 클레임에도
  실리지만 검사하는 곳은 없다. 즉 로그인만 하면 모든 명령을 쓸 수 있다. 운영자 여러 명이
  권한을 나눠 쓰는 상황을 전제하지 않기 때문이다.
- **비밀 관리.** `appsettings.json`의 개발 기본값이 평문이다(World 공유 시크릿, 토큰 서명키, DB
  비밀번호, 시드 계정). 로컬 루프백 전용이므로 이대로 두고, 필요하면 환경 변수로 덮어쓴다.
- **보상 종류.** 우편(`reward_kind = 'Mail'`)만 지원한다. 아이템·재화 지급은 게임 쪽에 해당
  시스템이 생긴 뒤의 일이다.

실제 운영에 쓸 물건으로 바꾼다면 위 세 가지가 먼저다.
