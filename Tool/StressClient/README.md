# StressClient

**동시 접속 부하 측정 도구.** 세션 수천~1만 개를 붙여서 처리량·지연·정합성 붕괴 지점을
찾는다. `Tool/ProtocolClient`가 프로토콜 한 번 왕복시켜 보는 REPL이라면, 이쪽은 같은 프로토콜을
대량으로 두드려서 **서버가 어디서 무너지는지**를 보는 쪽이다.

이 도구로 발견한 처리량 병목의 수정 계획이 `docs/load-test-fix-plan.md`에 있다.

## 빌드 / 실행

솔루션(`asio-server.slnx`) 빌드에 포함된다. 산출물은 `bin/x64/Debug/StressClient.exe`.
**측정할 때는 Release로 빌드할 것** — Debug 빌드의 클라이언트 자체 오버헤드가 서버 측정값을
가린다.

```
bat\start_server_all.bat
bin\x64\Release\StressClient.exe [host] [port] [세션수] [세션당사이클] [초당램프업] [스톨판정초] [최대수행초]
```

인자는 순서대로 위치 기반이고, 뒤쪽을 생략하면 기본값을 쓴다.

| 인자 | 기본값 | 의미 |
|---|---|---|
| `host` | `127.0.0.1` | 대상 주소 |
| `port` | `9000` | GatewayServer 포트 |
| `세션수` | `1000` | 동시 접속 세션 수. 1만까지 실측했다 |
| `세션당사이클` | `200` | 세션 하나가 수행할 Mail Add→Ack→Del→Ack 왕복 횟수 |
| `초당램프업` | `500` | 초당 새로 접속시킬 세션 수 |
| `스톨판정초` | `15` | 이 시간 동안 진전이 없는 세션을 "스톨(데드락 의심)"로 기록 |
| `최대수행초` | `300` | 전 세션이 못 끝내도 이 시간에 종료하고 요약을 낸다 |

예시:

```
REM 가볍게 확인
bin\x64\Release\StressClient.exe 127.0.0.1 9000 500 50

REM 1만 세션
bin\x64\Release\StressClient.exe 127.0.0.1 9000 10000 100 1000 30 600
```

## 램프업이 왜 인자인가

1만 세션을 한꺼번에 `connect`하면 서버의 accept 큐가 넘쳐 **접속 실패가 서버 처리 능력과
무관하게** 발생한다. 그러면 측정하려던 것(처리량·지연)이 아니라 accept 백로그 크기를 재게
된다. 초당 유입을 제한해서 접속 단계와 처리 단계를 분리하는 것이 `초당램프업`의 목적이다.

## 결과 읽는 법

종료 시 요약이 출력된다:

```
========== StressClient 결과 요약 ==========
시도/접속/완료 세션: ...
Mail Add 송신/Ack: ...
Mail Del 송신/Ack: ...
완료된 사이클 수: ...
불일치(id 안 맞음/삭제 실패) 총 건수: ...
스톨(데드락 의심) 세션 수: ...
브로드캐스트 전송 횟수: ...
브로드캐스트 기대/실제 수신 합계: ... (비율 ...)
소요 시간: ...초, 처리량: ... 사이클/초
---------- 지연(왕복 RTT, 클라이언트 체감) ----------
```

보는 순서는 **정합성 → 스톨 → 지연 → 처리량**이다:

1. **불일치 건수가 0이 아니면 처리량 숫자는 의미가 없다.** 받은 `mailId`가 보낸 것과 다르거나
   삭제가 실패한 것이므로, 부하 하에서 상태가 깨진 것이다. 상세는 로그에 세션·사이클 단위로
   남는다.
2. **스톨 세션 수**가 0이 아니면 어딘가 진전이 멈춘 것이다. 느린 것과 멈춘 것은 다른 문제라
   워치독으로 따로 잡는다.
3. **브로드캐스트 기대/실제 비율.** 존 브로드캐스트가 실제로 전원에게 닿았는지다. 1보다
   작으면 팬아웃이 유실되고 있다는 뜻이다.
4. **지연**은 평균이 아니라 꼬리를 본다. 평균이 멀쩡해도 p99가 튀면 특정 스레드가 밀리는
   것이고, 존 하나에 인구가 몰려 BASIC 스레드가 직렬화되는 상황이 여기서 드러난다.
5. **처리량**은 위 네 개가 다 정상일 때만 유효한 숫자다.

지연은 **클라이언트 체감 RTT**다 — 서버 내부 처리 시간이 아니라 송신부터 응답 수신까지이므로
네트워크·스케줄링 지연이 포함된다.

## 구조

| 파일 | 역할 |
|---|---|
| `Src/App/StressRunner.{h,cpp}` | 전체 조립: 램프업 접속, 워치독, 종료 판정, 요약 출력 |
| `Src/Session/StressSession.{h,cpp}` | 세션 하나의 상태 기계(접속 → 사이클 반복 → 종료) |
| `Src/Stats/StressStats.{h,cpp}` | 집계 지점. 카운터를 `std::atomic`으로 둬서 모든 세션이 락 없이 올린다 |
| `Src/Stats/LatencyHistogram.{h,cpp}` | 지연 히스토그램(백분위 계산용) |

세션마다 스레드를 만들지 않는다. `Shared/Core`의 `IoContextPool`로 I/O 스레드를 코어 수만큼만
두고 그 위에 세션 수천 개를 비동기로 다중화한다 — 1만 세션에 1만 스레드를 띄우면 컨텍스트
스위치 비용이 측정 대상을 압도해서, 클라이언트가 병목이 되어버린다.

## 한계

- 이동(`C2ZMove`)과 존 핸드오프는 부하 시나리오에 없다. Mail 왕복과 브로드캐스트 수신 확인이
  중심이다.
- 클라이언트와 서버를 같은 머신에서 돌리면 CPU를 나눠 쓰게 된다. 절대 수치보다 **수정 전후
  비교**에 쓰는 것이 이 도구의 용도다.
